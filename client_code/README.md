# PC CCTV 클라이언트

## Crop 수집 MVP 1단계 (2026-11-15)

각 카메라의 `VideoWorker`가 일반 클래스인 `storage/crop_collector.py`의 `CropCollector`를 각각 소유한다. 별도 crop 스레드·공유 큐 없이 기존 영상 작업 스레드에서 실행한다. **VLM OFF 상태에서도 YOLO가 켜져 있으면 crop을 수집한다.** 아래 다중카메라 개발 기록에서 crop을 후속 범위로 적은 내용은 이전 단계 당시의 기록이다. OSNet·글로벌 ID·새 이벤트·DB/API 연동은 아직 구현하지 않았다.

### 동작 및 저장 위치

- 인물별 최대 0.5초에 한 번 검사한다. 단조 증가 시계를 사용하며 누락된 시간의 프레임을 보충하지 않는다.
- 박스·글자를 그리기 전 원본 프레임의 bbox를 자른다. 최소 너비 64px, 높이 128px, 그레이스케일 Laplacian 분산 50 이상인 **첫 5장**을 모은다. 값은 `CropCollector` 생성자 기본값이며 실제 촬영 환경에 맞춘 튜닝은 남아 있다. 이 값이 재식별 정확도를 보장하지는 않는다.
- 기존 `FullBodyChecker`의 FULL/PARTIAL 화면 표시는 유지한다. 해당 휴리스틱은 새 crop 저장의 필수 조건이 아니다. 가림·자세 판별이나 전체 관측 중 최상위 5장 선별은 하지 않는다.
- 후보는 원본과 독립된 이미지 복사본으로 메모리에 유지한다. 5장이 모이면 JPEG로 저장하고 후보 이미지 메모리를 비운다. 같은 로컬 추적 대상의 추가 수집은 중단한다.
- 프로젝트 루트 기준 `output/camera_<ID>/YYYY-MM-DD/person_<로컬ID>_<HHMMSSmmm>/crop_01.jpg`부터 `crop_05.jpg`에 저장한다. 실행 위치·기존 녹화 경로 설정과 무관하다. 날짜·시각은 첫 관측 기준이며 이름 충돌 시 짧은 접미사를 붙인다. `output/`은 Git에서 제외한다.
- 임시 폴더에서 5장을 저장한 후 인물 폴더로 이름을 바꾼다. 실패 시 완료로 처리하지 않고 이번 저장의 임시 파일만 정리한다. 권한 문제·강제 종료로 임시 `.pending` 폴더가 남을 수 있으며 자동 복구는 구현하지 않았다.
- 저장 완료는 실행 콘솔의 `[Crop] ... 5장 저장 완료` 메시지로 확인한다. 별도 UI·이벤트 기능은 추가하지 않았다. 저장 실패는 기존 오류 전달 경로로 한 번 알리고, 해당 추적 대상은 자동 재시도하지 않는다. 영상 수신·추적은 계속한다.
- 5장 미만이면 파일을 저장하지 않는다. 기존 약 3초 인물 유실 정리, 추적 세대 변경, AI 비활성화, Worker 종료 시 후보를 폐기한다. 잠깐 사라져도 동일 로컬 추적이 유지되면 이어서 수집한다. 완료된 파일은 보존한다.
- 기존 원본 녹화·클립·궤적·레거시 VLM 경로와 저장 정책은 유지한다. 새 5장 묶음과 클립 연결은 후속 범위다.

### 검증 결과와 다음 작업

- 새 자동 테스트 7개 통과: 수집 간격, 크기·선명도 탈락, 프레임 복사, 5장 JPEG 디코딩, 한글 경로, 이름 충돌 시 기존 파일 보존, 부분 저장 실패·중복 재시도 방지, VLM OFF VideoWorker 연결, 겹치는 bbox의 주석 혼입 방지를 확인했다. 합성 입력과 임시 디렉터리를 사용했다.
- 전체 클라이언트 테스트 77개 중 74개 통과, 3개 실패. `VideoStream.open()`이 영상 파일에도 `CAP_DSHOW`를 지정하여 파일을 열지 못하는 기존 문제다. 실패한 3개는 수정 전 HEAD의 VideoWorker로도 동일하게 실패했다. 이번 작업에서 영상 입력 정책은 변경하지 않았다.
- 기존 웹캠 녹화본 재생 + 실제 YOLO/ByteTrack에서 새 crop 5장 저장·디코딩과 Worker 정리를 확인했다. 첫 crop은 직접 열어 박스·글자가 없는 것도 확인했다. 입력은 상반신 영상이므로 전신 crop 수집 검증은 아니다. 물리 카메라·GUI 조작 검증과 구분한다. 진단용 카메라 번호는 9901이며 입력 원본은 보존했다. 진단 어댑터가 종료 시 빈 프레임을 반환해 기존 웹캠 수신 실패 메시지가 한 번 발생했다. crop 저장 오류는 없었다. 원자료는 프로젝트 루트 `output/crop_stage1_replay_report.json`과 `output/camera_9901/`에 있다.
- 남음: 실제 단일 카메라의 crop 품질·저장 시 지연 확인, 품질 임계값 조정. 다음 2단계는 실제 두 카메라 격리·STOP/재시작·장애 조건 검증이다. 동기 JPEG 저장은 해당 VideoWorker를 잠시 지연시킬 수 있다. OSNet은 crop 결과를 확인한 다음 단계에서 연결한다.

## 다중카메라 개발 계획

2026-10-08 4단계 부분 실측: 실제 웹캠·YOLO26s CUDA 실행과 녹화본 두 입력의 GPU 부하·반복 종료를 확인했다. **엣지노드가 없어 실제 두 장치·통신 지연 2초 미만·단선 복구는 미검증**이다. 최신 수치·실행 방법·남은 항목은 [4단계 실측 기록](docs/MULTI_CAMERA_STAGE4_VALIDATION.md)을 읽는다. 아래 1~3단계의 미검증 표기는 각 단계 완료 당시 기록이다.

최대 두 대 동시 실행, 같은 관제 창의 전체 보기(4분할)·개별 보기, 카메라별 YOLO26s 및 기존 녹화·클립·궤적 처리를 개발할 때는 [다중카메라 개발 계획](docs/MULTI_CAMERA_DEVELOPMENT_PLAN.md)을 먼저 읽는다. 2026-10-08 현재 3단계 추적 격리·저장·단선 유실 처리까지 구현했고 4단계는 부분 실측했다. 최신 결과는 아래 `다중카메라 계획 4단계`와 개발 계획 12절을 따른다. 3단계 자동 검증과 4단계 실제 YOLO·웹캠/재생 입력 검증을 구분한다. VLM·이벤트 UI는 비활성화하며, crop 정책·새 이벤트 스키마·OSNet·CNN은 후속 범위다.

## 실행

기존 `venv311`을 사용한다. 새 패키지 설치 없이 PyQt5의 QtNetwork로 인증·카메라 관리 API에 연결한다. 백엔드 의존성이 없는 새 환경은 [백엔드 README](backend/README.md)의 설치 안내를 따른다.

PowerShell에서:

```powershell
cd C:\GitHub_Clone\AI_CCTV\client_code
..\venv311\Scripts\python.exe main.py
```

영상 모델 등 기존 상대 경로를 유지하기 위해 `client_code` 디렉터리에서 실행한다. 별도 서버 명령은 필요 없다.

- 클라이언트가 같은 가상환경의 Python으로 FastAPI 자식 프로세스를 실행한다. 서버 주소는 `http://127.0.0.1:8000`이다.
- 이미 별도 서버가 실행 중이면 해당 터미널에서 정상 종료한 후 클라이언트를 실행한다. 다른 서버에 자동으로 붙거나 임의로 종료하지 않는다.
- 프로세스 시작·서버 준비 확인 실패 시 연결 오류와 재시도 버튼을 표시한다.
- DB 경로는 기존 `backend/data/ai_cctv.db`를 유지한다. 기존 계정·미디어를 삭제하지 않는다.

## 화면 흐름

```text
프로그램 실행 → 백엔드 시작·준비 확인 → 가입 필요 여부 조회
  ├─ 관리자 없음 → 최초 회원가입 → 로그인
  ├─ 관리자 있음 → 로그인
  └─ 연결 실패 → 오류 안내·재시도

로그인 성공 → API 카메라 목록 조회 → 카메라 선택·등록·수정
  → START 전 최신 상세 확인 → 최대 두 대 실행
  → 전체 보기(4분할) / 개별 보기 전환 → 선택 카메라만 STOP
로그아웃 → 작업 정리 → 서버 세션 폐기·로컬 토큰 삭제 → 로그인 화면
프로그램 닫기 → 작업 정리 → 로그아웃 → 소유한 백엔드 종료 → 앱 종료
```

- 로그인·회원가입은 기존 남색 배경, 패널, 글꼴, 입력창과 버튼 테마를 사용한다.
- 아이디·비밀번호는 각각 최소 4자이며 회원가입 시 비밀번호 확인이 일치해야 한다. 서버에서도 같은 규칙을 검증한다.
- 가입은 자동 로그인이 아니다. 회원가입 성공 후 비밀번호를 지우고 로그인 화면으로 이동한다.
- 이미 계정이 생성된 경우의 `SIGNUP_CLOSED`는 로그인 화면으로 안내한다.
- 관제 창과 영상 작업은 로그인 전에 생성하지 않는다. 선택한 활성 카메라에 대해서만 START를 허용하고 실행 전 상세 API로 다시 확인한다.
- 카메라 등록 정보는 API로 DB에 저장한다. 분석·저장 옵션은 기존처럼 창의 메모리에 있으며 로그아웃 후 기본값을 사용한다. 이 옵션들의 영구 저장은 이번 범위에 포함하지 않는다.

## 인증과 HTTP

- [통합 API 명세서](docs/API_SPEC.md)의 인증 API 5개와 카메라 관리 API 4개를 호출한다. UI를 위한 API나 DB 테이블을 추가하지 않았다.
- HTTP는 `QNetworkAccessManager`의 비동기 요청으로 처리하며 기본 요청 제한 시간은 10초다. 리다이렉트로 자격증명을 다른 주소에 자동 전송하지 않는다.
- 중복 요청을 막고, 요청 중 입력·버튼을 비활성화한다. 비밀번호와 토큰을 화면·로그·파일에 출력하지 않는다.
- 토큰은 메모리에만 보관한다. 프로그램을 새로 실행하면 로그인해야 한다.
- 서버가 알려준 Access 만료 약 30초 전에 갱신한다. 만료가 임박하면 최소 1초 간격으로 조정한다.
- 갱신 후 Refresh 값을 교체하되 최초 로그인 기준 최대 8시간을 연장하지 않는다. 로컬 시간 관리는 단조 증가 시계를 사용한다.
- 일시적 갱신 네트워크 장애는 10초 후 재시도한다. 401·유효하지 않은 응답·최대 세션 시간 초과 시 관제 작업을 정리하고 재로그인을 요구한다.
- 로그아웃은 진행 중인 로그인·갱신 응답을 기다려 최신 Refresh 토큰으로 요청한다. 늦게 도착한 응답이 로그인 상태를 되살리지 않는다.
- 서버 로그아웃 확인에 실패해도 로컬 토큰은 삭제한다. 이때 서버 세션 폐기는 확인되지 않았다는 안내를 남긴다.

## 작업 정리와 제한

- 로그아웃·창 닫기 중에는 START·설정 등 새 작업을 차단한다. GUI에서 `wait()`로 스레드 종료를 기다리지 않는다.
- 영상 루프는 예외가 발생해도 녹화·클립 정리와 스트림 해제를 시도한다. RTSP·VLM·복구 작업의 실제 종료까지 확인한 뒤 다음 화면으로 이동한다.
- VLM 추론·모델 로딩은 강제 중단하지 않는다. 실행 중인 분석 스레드가 끝나기 전에 모델을 해제하지 않는다. 대기 중 분석은 새로 시작하지 않는다.
- 리소스 모니터 타이머와 요청도 종료한다. 열린 설정 창도 닫는다.
- 30초 이상 지연되면 대기 안내를 표시하며 GUI는 계속 응답한다. 분석·드라이버·복구 요청이 반환하지 않으면 정리 대기가 계속될 수 있다. 작업 스레드를 강제 종료하거나 종료 성공으로 간주하지 않는다.
- 정리 중 예외를 확인하면 화면 전환을 차단하고 실패 안내를 표시한다. 실제 디스크 오류의 복구 기능은 추가하지 않았다.
- 백엔드는 로그아웃 시 유지한다. 프로그램 종료 시 stdin으로 정상 종료를 요청하고, 10초 내 종료되지 않을 때만 자신이 만든 자식 프로세스를 종료한다. 강제 종료 이력은 다음 서버 실행에서 `interrupted`로 정리된다.

## 다중카메라 계획 2단계: 두 실행과 전체/개별 보기 (2026-10-08)

### 사용 방법과 실행 정책

1. 로그인 후 카메라를 선택하고 START한다. 다른 카메라를 선택해 START하면 최대 두 대가 실행된다. 등록 개수는 제한하지 않는다.
2. 왼쪽 `전체 보기`는 2×2 네 칸을 표시한다. 최대 두 칸에서 카메라를 실행하고 나머지는 `미사용`이다. 전체 보기에서는 START/STOP·모니터를 사용할 수 없다.
3. 카메라 선택은 표시만 바꾼다. 숨겨진 카메라의 Worker와 저장은 계속되며 실행 ID·저장 폴더는 유지된다. STOP은 선택한 카메라만 정리한다.
4. 상세 조회·연결 준비·재연결·정리 중에도 슬롯을 점유한다. 중복 START·세 번째 START는 관리자에서도 차단한다. 실패한 조회는 예약을 반환하고 정리 실패는 해당 슬롯을 유지한다.
5. 설정·카메라 관리·목록 새로고침은 모든 실행·상세 요청·모니터가 정리된 상태에서 허용한다. 실행 중에도 목록 선택과 다른 카메라의 STOP은 가능하다.
6. 모니터는 한 창이며 열 때의 카메라에 고정된다. 다른 카메라를 선택해도 대상은 바뀌지 않는다. 대상 STOP은 모니터 종료까지 기다리고 다른 카메라 STOP은 기다리지 않는다.
7. 이벤트 타임라인·인물 이벤트 카드·출현/사라짐/누적 집계는 제거했다. 카메라별 현재 탐지 인원과 연결·오류 안내는 유지한다. VLM은 OFF다. 이벤트 표시 제거는 기존 Worker의 인물 정리·클립·궤적 중단을 의미하지 않는다.

- `CameraView`가 카메라별 최신 표시 이미지를 소유한다. GUI 스레드에서 이미지 사본을 만들고 종횡비를 유지하며, 동일 위젯을 전체/개별 보기에서 재배치한다. 연결 대기·장애·중지 상태에서는 이전 LIVE 프레임을 지운다.
- 전체 클라이언트 테스트 54개 통과. 두 슬롯 예약·취소·실패·개별 정리·재시작, 위젯 재사용·카메라별 프레임/통계, 모니터 격리, 두 Worker 종료 후 로그아웃, 실제 HTTP 동시 상세 조회의 단일 토큰 갱신을 검증했다.
- `tests/test_multi_camera.py`는 두 임시 MJPEG 영상을 실제 OpenCV로 읽고 AI OFF로 동시에 저장한다. 숨겨진 입력의 계속 처리, 한 대 STOP·재시작 중 다른 입력 유지, 실행별 MP4 재생 가능 여부와 전체 정리를 확인한다. 유한 합성 파일의 수신 속도를 테스트용으로 조절하며 실제 장치 FPS·녹화 품질 측정은 아니다.
- 4분할·개별 보기·크기 변경 자동 검증과 Windows Qt 렌더러의 합성 화면 배치를 확인했다. 사용자 장치에서 직접 조작한 검증과 구분한다.
- 기존 실행 명령과 의존성은 동일하다. 백엔드 코드·DB·API 계약을 변경하지 않았다.

### 2단계 완료 당시 남은 범위

3단계의 YOLO 동시 실행·추적 상태·인물 클립/궤적 격리 검증, 단선 중 인물 유실 정리, 저장 실패 전달 보완은 진행하지 않았다. 실제 웹캠·RTSP·GPU 성능·단선 복구도 미검증이다. 장치에서 우선 설정의 YOLO를 끄고 두 카메라 START → 전체/개별 보기 → 개별 STOP·재시작 → 로그아웃 순서로 확인한다.

## 다중카메라 계획 3단계: 추적 격리·저장·유실 처리 (2026-10-08)

### 구현

- Worker별 YOLO 모델·인물 상태·저장 관리자를 유지한다. 설치된 Ultralytics 8.4.77의 ByteTrack은 전역 ID 카운터를 생성/초기화 시 공유하므로 `detection/isolated_byte_tracker.py`에서 ID 발급만 인스턴스별로 격리했다. 매칭·칼만 필터 등 기존 ByteTrack 알고리즘은 그대로 사용한다. `PersonTracker`의 시작 콜백으로 해당 모델에만 연결하며 라이브러리 전역 변경은 하지 않는다.
- 프레임이 없어도 기존 3초 유실 기준으로 인물 상태·ID 연결을 제거하고 클립·궤적을 마무리한다. 새 프레임의 추적 전에 만료를 확인하므로 오래된 raw ID가 돌아와도 종료된 관측을 이어 쓰지 않는다. 3초 이상 추론 입력 공백 후에는 해당 ByteTrack 상태를 초기화하고 `tracking_generation`을 증가시킨다. 모델 재로딩 없이 로컬 ID 번호는 계속 증가한다. 한 프레임에서 두 인물에게 같은 보정 ID를 부여할 수 있던 오래된 raw ID 연결도 제거했다.
- 수신기가 연결 상태를 유지해도 3초 이상 새 프레임이 없으면 해당 카메라를 연결 대기로 표시한다. 현재 인원 표시·모니터 대상 고정은 2단계 구현을 유지한다. 새 프레임 없는 상태에서 탐지 인원을 임의로 생성하지 않는다.
- 원본 분할, 전체 프레임 `preview.mp4` 최대 길이, 클립 종료 후 궤적 수집, bbox 하단 중앙점·샘플링·평활화 정책은 유지한다. 원본 파일의 시작 시각에 마이크로초를 포함해 같은 초의 STOP/재연결 파일 충돌을 방지한다. 궤적은 JPEG 인코딩 후 파일로 기록하여 한글 경로와 쓰기 실패를 처리한다.
- Writer 열기, 파일 이름 변경, 궤적 인코딩·기록에서 확인한 실패를 숨기지 않는다. 영상 처리 중 저장 실패는 해당 Worker를 종료·정리하고 카메라별 오류로 안내한다. 한 클립의 종료 실패에도 나머지 인물 종료와 스트림 해제를 시도하며 마무리 실패는 `정리 실패`로 남긴다. 다른 카메라의 실행·STOP은 유지된다.
- 복구 요청의 예외도 카메라별로 안내하며 STOP 중 발생한 저장 실패는 정리 후에도 표시한다. 복구 ZIP은 실행 폴더의 `복구 영상`, 병합 MP4는 같은 실행 폴더의 `원본 녹화본`에 저장하는 기존 정책이다. 저장 루트 미설정 시 원본·클립·복구는 생성하지 않는다.
- 종료 시 Worker의 추적기 참조와 인물 상태를 해제한다. VLM OFF·이벤트 UI 제거를 유지하며 백엔드·API·DB·의존성 변경은 없다.

### 검증과 제한

- 클라이언트 전체 70개 테스트 통과(기존 54개 + 3단계 16개). 실행 명령은 위 검증 절과 동일하다. `git diff --check`도 통과했다.
- `tests/test_tracking_storage.py`: 실제 ByteTrack에 합성 탐지를 입력해 두 카메라의 생성·초기화에 따른 ID 격리를 확인했다. 모델은 가짜 YOLO로 대체하여 콜백 연결·긴 공백·ID 재등장·프레임 없는 유실 정리·저장 실패·종료 실패·저장 미설정 조건을 검증했다.
- `tests/test_multi_camera.py`: 두 합성 영상을 실제 OpenCV로 읽고 가짜 모델로 각각 두 인물을 반환했다. 같은 로컬 ID의 원본·클립·궤적 분리, 숨겨진 영상 처리, 개별 STOP·재시작, 모든 MP4 재읽기와 JPEG 디코딩을 확인했다. 기존 AI OFF·현재 인원·모니터·인증·종료 회귀도 통과했다.
- 복구 테스트는 가짜 HTTP 응답의 ZIP 저장·압축 해제와 병합 대상 경로를 확인하며 FFmpeg 병합 호출은 대체했다. 실제 장치 복구 API·실제 TS 병합 성공을 의미하지 않는다.
- 실제 YOLO 가중치 추론, 웹캠·RTSP, GPU 동시 실행·장시간 메모리·처리 성능은 실행하지 않았다. OpenCV가 반환값/예외 없이 내부에서 놓치는 디스크·인코더 오류나 물리 디스크 내구성을 보장하지 않는다. ByteTrack 연결은 설치된 8.4.77로 검증했으므로 라이브러리 변경 시 관련 테스트를 다시 실행한다.
- 다음 단계는 별도 요청 후 진행할 4단계 실제 장치·성능 검증이다. crop 정책·새 이벤트·OSNet·CNN·Flutter 송출은 추가하지 않았다.

## 다중카메라 계획 4단계: 실제 장치·성능 부분 검증 (2026-10-08)

- 실제 웹캠 1280×720: AI OFF 16.53 FPS, 최초 AI ON 8.80 FPS. 재시작 AI ON은 15.94/7.56 FPS로 변동했다. 실제 YOLO26s는 RTX 3050 Laptop GPU의 `cuda:0`에서 실행됐다. 뒤의 웹캠 시험에서는 인물 클립·궤적도 생성·재읽기했다.
- 같은 웹캠 녹화본의 보조 비교: 한 모델 ON 22.62 FPS, 두 입력 OFF 각각 23.80 FPS, 두 모델 ON 각각 16.37/16.32 FPS. **로컬 재생 결과를 실제 두 장치나 네트워크 처리 성능으로 해석하지 않는다.**
- 두 모델 세 차례, 실제 웹캠 두 차례의 동일 프로세스 재시작과 정상 정리를 확인했다. 종료 후 CUDA 할당은 각각 64 MiB/32 MiB로 반복 사이 유지됐지만 짧은 관측이며 장시간 누수 검증은 아니다.
- 실측에서 생성한 MP4 51개와 궤적 JPEG 12개를 읽었고 저장 오류는 없었다. 최초 AI 실행의 원본 10초 구간이 약 7.17초로 재생되는 한계도 확인했다. 디코딩 성공을 무손실 녹화로 설명하지 않는다.
- 목표는 버벅임 최소화·통신 지연 2초 미만이다. 실제 엣지노드·네트워크·촬영 시각 계측이 없어 지연 목표는 판정할 수 없으며 실제 두 장치·단선/복구·관제 창 조작·장시간 검증은 남아 있다. **4단계 전체 완료가 아니다.**
- 수동 측정은 `tests/manual_multi_camera_probe.py`, 원자료는 `outputs/stage4/`, 환경·측정 정의·제한·명령은 [4단계 실측 기록](docs/MULTI_CAMERA_STAGE4_VALIDATION.md)에 있다. 진단 스크립트 외 제품 처리 코드·DB·API·의존성은 변경하지 않았다.
