# PC CCTV 클라이언트

## 다중카메라 개발 계획

최대 두 대 동시 실행, 같은 관제 창의 전체 보기(4분할)·개별 보기, 카메라별 YOLO26s 및 기존 녹화·클립·궤적 처리를 개발할 때는 [다중카메라 개발 계획](docs/MULTI_CAMERA_DEVELOPMENT_PLAN.md)을 먼저 읽는다. 단계별 계획과 진행 기록이며, 2026-10-08 현재 1단계 실행 관리자 분리까지 구현했다. 동시 실행은 아직 한 대다. 이번 계획에서는 VLM·이벤트 UI를 비활성화하고, crop 정책·새 이벤트 스키마·OSNet·CNN은 후속 단계로 분리한다.

## 실행

기존 `venv311`을 사용한다. 새 패키지 설치 없이 PyQt5의 QtNetwork로 인증·카메라 관리 API에 연결한다. 백엔드 의존성이 없는 새 환경은 [백엔드 README](backend/README.md)의 설치 안내를 따른다.

PowerShell에서:

```powershell
cd C:\GitHub_Clone\AI_CCTV\client_code
..\venv311\Scripts\python.exe main.py
```

영상 모델 등 기존 상대 경로를 유지하기 위해 `client_code` 디렉터리에서 실행한다. 별도 서버 명령은 필요 없다.

- 클라이언트가 같은 가상환경의 Python으로 FastAPI 자식 프로세스를 실행한다. 서버 주소는 `http://127.0.0.1:8000`이다.
- 이미 별도 서버가 실행 중이면 해당 터미널에서 정상 종료한 후 클라이언트를 실행한다. 다른 서버에 자동으로 붙거나 임의로 종료하지 않는다.
- 프로세스 시작·서버 준비 확인 실패 시 연결 오류와 재시도 버튼을 표시한다.
- DB 경로는 기존 `backend/data/ai_cctv.db`를 유지한다. 기존 계정·미디어를 삭제하지 않는다.

## 화면 흐름

```text
프로그램 실행 → 백엔드 시작·준비 확인 → 가입 필요 여부 조회
  ├─ 관리자 없음 → 최초 회원가입 → 로그인
  ├─ 관리자 있음 → 로그인
  └─ 연결 실패 → 오류 안내·재시도

로그인 성공 → API 카메라 목록 조회 → 카메라 선택·등록·수정
  → START 전 최신 상세 확인 → 선택한 카메라 한 대 실행 → STOP 완료 후 전환
로그아웃 → 작업 정리 → 서버 세션 폐기·로컬 토큰 삭제 → 로그인 화면
프로그램 닫기 → 작업 정리 → 로그아웃 → 소유한 백엔드 종료 → 앱 종료
```

- 로그인·회원가입은 기존 남색 배경, 패널, 글꼴, 입력창과 버튼 테마를 사용한다.
- 아이디·비밀번호는 각각 최소 4자이며 회원가입 시 비밀번호 확인이 일치해야 한다. 서버에서도 같은 규칙을 검증한다.
- 가입은 자동 로그인이 아니다. 회원가입 성공 후 비밀번호를 지우고 로그인 화면으로 이동한다.
- 이미 계정이 생성된 경우의 `SIGNUP_CLOSED`는 로그인 화면으로 안내한다.
- 관제 창과 영상 작업은 로그인 전에 생성하지 않는다. 선택한 활성 카메라에 대해서만 START를 허용하고 실행 전 상세 API로 다시 확인한다.
- 카메라 등록 정보는 API로 DB에 저장한다. 분석·저장 옵션은 기존처럼 창의 메모리에 있으며 로그아웃 후 기본값을 사용한다. 이 옵션들의 영구 저장은 이번 범위에 포함하지 않는다.

## 인증과 HTTP

- [통합 API 명세서](docs/API_SPEC.md)의 인증 API 5개와 카메라 관리 API 4개를 호출한다. UI를 위한 API나 DB 테이블을 추가하지 않았다.
- HTTP는 `QNetworkAccessManager`의 비동기 요청으로 처리하며 기본 요청 제한 시간은 10초다. 리다이렉트로 자격증명을 다른 주소에 자동 전송하지 않는다.
- 중복 요청을 막고, 요청 중 입력·버튼을 비활성화한다. 비밀번호와 토큰을 화면·로그·파일에 출력하지 않는다.
- 토큰은 메모리에만 보관한다. 프로그램을 새로 실행하면 로그인해야 한다.
- 서버가 알려준 Access 만료 약 30초 전에 갱신한다. 만료가 임박하면 최소 1초 간격으로 조정한다.
- 갱신 후 Refresh 값을 교체하되 최초 로그인 기준 최대 8시간을 연장하지 않는다. 로컬 시간 관리는 단조 증가 시계를 사용한다.
- 일시적 갱신 네트워크 장애는 10초 후 재시도한다. 401·유효하지 않은 응답·최대 세션 시간 초과 시 관제 작업을 정리하고 재로그인을 요구한다.
- 로그아웃은 진행 중인 로그인·갱신 응답을 기다려 최신 Refresh 토큰으로 요청한다. 늦게 도착한 응답이 로그인 상태를 되살리지 않는다.
- 서버 로그아웃 확인에 실패해도 로컬 토큰은 삭제한다. 이때 서버 세션 폐기는 확인되지 않았다는 안내를 남긴다.

## 작업 정리와 제한

- 로그아웃·창 닫기 중에는 START·설정 등 새 작업을 차단한다. GUI에서 `wait()`로 스레드 종료를 기다리지 않는다.
- 영상 루프는 예외가 발생해도 녹화·클립 정리와 스트림 해제를 시도한다. RTSP·VLM·복구 작업의 실제 종료까지 확인한 뒤 다음 화면으로 이동한다.
- VLM 추론·모델 로딩은 강제 중단하지 않는다. 실행 중인 분석 스레드가 끝나기 전에 모델을 해제하지 않는다. 대기 중 분석은 새로 시작하지 않는다.
- 리소스 모니터 타이머와 요청도 종료한다. 열린 설정 창도 닫는다.
- 30초 이상 지연되면 대기 안내를 표시하며 GUI는 계속 응답한다. 분석·드라이버·복구 요청이 반환하지 않으면 정리 대기가 계속될 수 있다. 작업 스레드를 강제 종료하거나 종료 성공으로 간주하지 않는다.
- 정리 중 예외를 확인하면 화면 전환을 차단하고 실패 안내를 표시한다. 실제 디스크 오류의 복구 기능은 추가하지 않았다.
- 백엔드는 로그아웃 시 유지한다. 프로그램 종료 시 stdin으로 정상 종료를 요청하고, 10초 내 종료되지 않을 때만 자신이 만든 자식 프로세스를 종료한다. 강제 종료 이력은 다음 서버 실행에서 `interrupted`로 정리된다.

## PyQt 카메라 관리 1단계 (2026-10-07)

- `cameras/api_client.py`: QtNetwork 비동기 GET/POST/PATCH, Access 인증, 요청 취소와 늦은 응답 무시를 처리한다. 401일 때 SessionManager의 갱신을 공유하고 한 번만 재시도한다. 네트워크 실패한 저장 요청은 자동 재전송하지 않는다.
- `ui/camera_management.py`: 설정의 카메라 관리 페이지. 목록·상세·신규 등록·부분 수정·비활성화를 제공한다. 저장 실패 시 입력을 유지하고 서버 오류 코드는 로컬 안내 문구로 표시한다. 저장 응답을 잃었을 경우 새로고침으로 반영 여부를 확인한다.
- `ui/gui.py`: API 목록과 선택 ID, 빈 목록·조회 실패 구분, 비활성 카메라 표시, 저장 후 선택·목록 갱신을 구현했다. 목록 새로고침 시 존재하는 선택을 유지한다. 조회 실패 시 기존 목록을 보존하고 실패 안내를 표시한다.
- `ui/settings_window.py`: 카메라 관리 / 분석 설정 / 저장 설정으로 분리했다. 카메라 저장은 서버에 즉시 반영하며 창을 닫아도 취소되지 않는다. 분석·저장 옵션은 각 페이지의 적용 동작을 유지한다.
- `app_controller.py`: 로그인 성공 후 기존 세션을 관제 화면에 연결한다. 로그아웃·종료 시 기존 Worker 정리 순서를 유지하고 카메라 요청을 취소한다.

### 현재 실행 정책

- START는 활성 카메라 선택 후 가능하다. 실행 전 상세 API에서 최신 장치 번호·RTSP 주소·사용 여부를 확인하며 조회 실패·비활성 상태에서는 실행하지 않는다.
- 한 번에 한 카메라만 실행한다. 실행·상세 조회·중지 처리 중에는 선택과 설정 변경을 막는다. 모니터링 창이 열려 있을 때도 카메라 전환 전에 창을 닫도록 한다.
- 대기 중은 등록 정보에 대한 표시이며 연결 성공이 아니다. LIVE는 프레임 도착으로 표시한다. AI 실패로 일반 CCTV 모드가 되어도 영상 연결 상태는 유지한다. 장애 구간 파일 복구 완료는 LIVE 상태를 직접 변경하지 않는다.
- STOP은 진행 중 상세 요청 취소, Worker 종료 요청, 녹화·VLM·복구·모니터링 종료 확인 순으로 처리한다. 실행 세대 번호로 늦은 프레임·이벤트를 무시한다. 정리 실패 시 재실행·전환을 막는다.

## 선택 카메라 런타임 연결 2단계 (2026-10-07)

- `ui/gui.py`: 상세 조회 → 카메라 정보 복사 → Worker 실행을 연결했다. 선택 ID와 실행 중 정보를 구분하고 선택 변경 시 이전 화면을 지운다. 실행 시작마다 통계·이벤트 표시를 초기화한다. 목록의 상태는 PyQt 메모리에만 보관한다.
- `workers/video_worker.py`: camera_id와 edge_api_base_url을 전달받는다. 장치 API 주소가 있고 RTSP·녹화가 설정된 경우에만 `{edge_api_base_url}/recover`를 사용한다. 복구 카메라 식별자도 고정 cam01 대신 등록 ID를 반영한다.
- `ui/resource_monitor_window.py`: 등록한 장치 API 주소의 `/monitor/resources`를 사용한다. 주소 미등록 시 장치 조회를 하지 않고 로컬 PC 리소스만 표시한다. 실행 중에는 시작 시 확정한 카메라 설정을 사용한다.
- 웹캠 프레임 수신 실패는 무한 오류 카드 반복 대신 Worker를 종료하며, 장치를 확인한 뒤 START로 재시도한다. RTSP는 기존 재연결을 유지한다.
- `video/video_stream.py`, `video/rtsp_receiver.py`: rtsps도 RTSP 수신기로 분류한다. 명시된 포트만 TCP 사전 확인하며, 포트 생략 시 8554를 임의로 가정하지 않고 OpenCV/FFmpeg 기본값에 맡긴다. IPv6 명시 주소도 TCP 확인 가능하다. 재연결 시 이전 프레임을 비우며 원본 RTSP URL 출력은 제거했다.

### 새 저장물 위치

```text
선택한 AI_CCTV 저장 경로/
  cameras/camera_<DB ID>/<실행별 UUID>/
    crops/
    원본 녹화본/
    이벤트 CLIP/
    복구 영상/
```

기존 저장 파일은 이동·삭제하지 않는다. 녹화와 복구는 같은 실행 폴더를 사용한다. 저장 경로 미설정 시 녹화·복구는 하지 않으며 기존 분석용 crop은 실행 위치와 무관한 `client_code/outputs/cameras/camera_<ID>/<UUID>/crops` 아래에 저장한다. UUID는 로컬 파일 격리용이며 향후 이벤트 API의 tracking_run_id를 대신하지 않는다.

## 다중카메라 계획 1단계: 실행 관리자 분리 (2026-10-08)

- `CCTVMainWindow.runtime`의 `CameraRuntimeManager`가 상세 조회, 시작 시 설정 복사, Worker 생성·신호 연결, 연결 상태, 실행 세대 번호, STOP 타이머와 종료 확인을 소유한다. GUI의 기존 `worker` 호환 필드는 남기지 않았다.
- 이번 단계는 한 대 실행을 유지한다. 조회 중·실행 중·정리 중 추가 START를 관리자에서도 거부한다. 실행 중 카메라 선택·설정 잠금도 유지한다.

- 검증: 클라이언트 전체 45개 테스트 통과(기존 36개 + 관리자 경계 7개 + 세션 종료 회귀 2개). 중복 시작, 설정 복사, 잘못된 상세, 생성 실패, 취소·재시작 이후 늦은 신호, 모니터 대기, 정리 실패, 세션 만료·로그아웃 순서를 확인했다. 기존 임시 백엔드 HTTP와 합성 영상 OpenCV 검증도 포함한다.
