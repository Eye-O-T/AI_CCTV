# PC CCTV 클라이언트

## 이벤트 MVP 4단계: 인물 이벤트·미디어 자동 갱신 (2026-11-20)

이벤트 기능을 개발하거나 다음 단계를 시작할 때 [이벤트 MVP 개발 계획](docs/EVENT_MVP_DEVELOPMENT_PLAN.md), [DB 스키마](docs/BACKEND_SCHEMA.md)의 events 절, [API 명세](docs/API_SPEC.md)의 이벤트 절을 먼저 읽는다. 네 종류의 Event 모델·DTO·Repository·Service와 Access 인증된 생성/미디어 갱신/목록/상세 API, 저장소 GET/PUT 설정을 구현했다. 등록 모델은 5개이며 운영 DB·설정·기존 미디어는 변경하지 않고 임시 DB/설정/파일·실제 로컬 HTTP로 검증했다. 다음 제품 서버 실행 시 없는 events 테이블을 추가한다.

저장소 절대 경로는 백엔드 DB 옆 ai_cctv.storage.json으로 유지하며 첫 이벤트 저장 뒤 다른 경로로 변경하지 못한다. 상대 경로는 지정된 AI_CCTV 아래 실제 완료 파일의 위치만 받는다. API 확인 방법·검증 결과는 [백엔드 README](backend/README.md#이벤트-mvp-2단계-api저장소-설정)와 개발 계획을 따른다.

PyQt 로그인 후 백엔드 저장소를 복원하고, 설정 저장 성공 확인 전에는 START를 막는다. 첫 프레임 수신에 camera_started, 사용자 STOP/정상 앱 종료의 정리 완료에 camera_stopped를 공용 비동기 큐로 저장한다. 재연결·시작 실패·오류/정리 실패를 정상 중지로 기록하지 않는다. 영상 정리 후 이벤트 큐를 최대 8초 마무리한 다음 로그아웃한다. 실패/시간 초과는 안내하고 다음 로그인에 작업을 재전송하지 않는다. 기존 ReID·파일 저장 구조는 유지한다. 4단계에서 글로벌 ID 확정 시 첫 탐지 시각의 등장, 정상 수신 중 자연 유실 시 마지막 탐지 시각의 사라짐, 파일 완료/폴더명 변경의 미디어 PATCH를 연결했다. STOP·끊김·추적 초기화는 미디어만 마무리하고 사라짐을 만들지 않는다. 등장 저장 확인 이후 종속 요청을 처리하며 종료 중 마지막 알림도 수집한다. 5단계는 사용자가 지정하면 진행한다. 전체 MVP도 JSON 조회까지이며 PyQt 이력 UI·Flutter·알림/푸시·미디어 파일 응답은 후속 범위다. 기존 설정/실패 안내 UI는 연결에 필요한 범위에서 조정할 수 있다.

4단계 신규 19개와 관련 회귀 147개, 서로 다른 검증 166개를 확인했다. 임시 HTTP·실제 ClipManager 파일과 폴더 rename 경합·부분 이동 실패·종료 중 저장 순서를 확인했고 최종 MP4/JPEG 디코딩과 OSNet용 5장 원본 보존도 검증했다. 기존 CAP_DSHOW 파일 입력 3개는 제외했다. 실제 웹캠/RTSP/OSNet·제품 GUI 직접 조작은 미검증이며 과거 단일 웹캠 부분 결과와 구분한다. 상세 실행/재검증 내역은 개발 계획 4단계 기록을 따른다.

멀티카메라 글로벌 인물 ID 작업 전에는 [글로벌 인물 개발 계획](docs/GLOBAL_PERSON_DEVELOPMENT_PLAN.md)을 읽는다. 2026-11-19 5단계 Local/Global 영상 표시까지 구현했으며 라벨·pipeline·crop 관련 37개를 확인했다. 사용자 실촬영에서 두 카메라의 단일 인물이 Global 1에 연결됐다(유사도 0.936/0.904, 저장 완료 후 반영 328/329ms). 다른 사람·동시 두 사람·지속 성능은 미검증이다. 이전 CAP_DSHOW 영상 파일 입력 실패 3개는 그대로 구분한다. 사용법은 [reid/README.md](reid/README.md)를 따른다.

## 저장 구조 변경 4단계: 실제 단일 웹캠 부분 검증 (2026-11-19)

실제 저장 구조 검증 결과와 재실행 전에는 [저장 구조 4단계 검증 기록](docs/STORAGE_LAYOUT_STAGE4_VALIDATION.md)을 읽는다. 현재는 **부분 검증이며 전체 완료가 아니다.** 사용자와 협의한 노트북 웹캠 1대로 실제 YOLO/OSNet·별도 임시 백엔드 HTTP·원본 분할·이벤트 이동·STOP/재시작을 실행했다. 운영 DB와 기존 미디어는 보존했고 제품 코드는 변경하지 않았다.

- 같은 볼륨의 진단 저장 경로에서 글로벌 ID별 완성 이벤트 관측 2건을 서로 다른 시도에서 확인했다. 원본/클립 MP4 13개와 계산용 crop/대표 crop/궤적 JPEG 17개를 모두 디코딩했다. 미확정 자료 temp 보존·정상 작업 종료와 운영 DB 불변도 확인했다.
- 최초/재시작 중 한쪽에서 crop 5장이 모이지 않아 **재시작 전후 글로벌 ID 유지 검증은 남아 있다.** 첫 프레임 수신 실패도 재현됐으며, 마지막 시도에서는 최초 1280×720/재시작 640×480으로 입력 크기가 달랐다. 상세 원인과 무손실 녹화·지속 성능을 확인한 것은 아니다.
- `tests/manual_storage_layout_probe.py`로 재현할 수 있다. 실제 장치가 필요한 진단이므로 자동 unittest에 포함하지 않는다. 제품 GUI 직접 조작·두 카메라·RTSP·장시간 검증은 남아 있다. 3단계 자동 검증 87개는 제품 코드 변경이 없어 반복하지 않았다.

## 저장 구조 변경 3단계: 글로벌 인물별 완료 자료 이동 (2026-11-19)

저장 구조를 수정하거나 결과 파일을 찾을 때 이 절을 먼저 읽는다. 현재는 아래 1·2단계의 파일 준비에 글로벌 ID별 최종 이동을 연결했다. 이벤트 DB/API는 추가하지 않았다.

```text
사용자가 지정한 위치/AI_CCTV/
├─ 원본 녹화본/YYYY-MM-DD/camera_ID/시작시각~종료시각.mp4
└─ 이벤트/person_12/2026-11-19/camera_7/
   └─ 14시03분12초~14시04분25초/
      ├─ clip.mp4
      ├─ crop.jpg
      └─ trajectory.jpg
```

### 이동과 종료 정책

- 카메라/실행/추적 세대/로컬 ID와 crop 작업 UUID가 모두 일치하는 현재 매칭 결과만 ClipManager 관측에 연결한다. 확정 글로벌 ID를 재사용하며 저장 때문에 새 글로벌 ID를 만들지 않는다. 중복 결과로 중복 저장하거나 다른 ID로 재할당하지 않는다.
- 글로벌 ID가 확정되면 이미 완료된 자료를 이동하고, 이후 완료되는 자료도 각각 이동한다. 기록 중인 클립은 이동하지 않는다. `이벤트/person_ID/추적 시작 날짜/camera_ID/추적 시작 시각/` 폴더를 처음 필요한 시점에 생성한다. 사용자 위치에 `.pending` 파일이나 기록 중인 영상을 두지 않는다.
- 추적 종료(인물 유실·STOP·세대 초기화) 시 궤적 저장을 마치고 폴더명을 `시작시각~마지막 관측 시각`으로 확정한다. 마지막 관측은 종료 처리 시각이 아니라 마지막 탐지 시각이다. 자정을 넘기면 시작 날짜 아래에 두고 종료 부분에 날짜를 포함한다. 클립 최대 길이는 기존 설정을 따르므로 폴더의 추적 구간 전체와 다를 수 있다.
- 같은 시작/종료 시각의 폴더가 이미 있으면 `_2`, `_3` 순번으로 별도 관측을 만든다. 다른 카메라/재시작/추적 세대의 자료를 합치지 않고 기존 폴더·파일을 덮어쓰지 않는다. 사용자 폴더명에는 UUID를 넣지 않는다.
- Windows `os.rename`으로 같은 볼륨 내 이동하며 다른 볼륨으로 복사하지 않는다. 성공한 파일의 현재 위치를 기록해 다음 완료 알림에서 다시 이동하지 않는다. `media_ready`의 경로는 알림 시점의 경로이며, 폴더명 확정 후 알림에서는 변경된 경로를 전달한다. `global_person_id`, `move_failed`로 연결/이동 오류를 구분한다.
- 정상 종료 후 이동이 끝난 관측의 **빈 temp 폴더만** 제거한다. 다른 파일·부분 파일이 남으면 보존한다. 글로벌 ID 미확정·5장 미수집·매칭 실패·종료 후 늦은 매칭 결과는 최종 이동 대상으로 삼지 않고 temp 자료를 보존한다. 정상적으로 매칭되었지만 대표 crop 복제만 실패하면 완료된 클립/궤적은 이동할 수 있으며 crop은 빠진 상태로 오류를 안내한다.
- 개별 파일 이동 실패는 해당 temp 원본을 보존하고 다른 완료 자료는 계속 이동한다. 이미 이동한 파일을 되돌리거나 실패 파일을 자동 재이동하지 않는다. 폴더명 확정 실패 시 이미 저장한 파일은 사용자 위치의 시작 시각 폴더에 그대로 남는다. 목적지 생성 실패·볼륨 불일치·파일 충돌도 오류로 안내한다.
- 이동/폴더명 확정 실패 이력이 있는 Worker는 STOP 시 정리 성공으로 처리하지 않고 기존 `정리 실패` 경로를 따른다. 다른 카메라의 실행과 자료는 유지한다. 자동 재시도·재시작 파일 복구·기존 자료 일괄 이동은 구현하지 않았다.
- OSNet용 원본 crop 5장의 프로젝트 `output` 저장, 일반 원본 녹화 이동, 활성 VLM·장애 복구 영상의 기존 경로, 인증·DB/API는 유지한다. 이벤트 테이블·이력/미디어 API는 별도 후속 작업이다.

### 검증과 남은 범위

## 저장 구조 변경 2단계: 인물 자료의 temp 저장·완료 상태 (2026-11-19)

이 절은 2단계 당시 파일 준비 구현 기록이다. 현재 글로벌 ID별 최종 이동은 위 3단계 절을 따른다.

```text
프로젝트/temp/YYYY-MM-DD/camera_ID/
└─ 실행_14시00분00초_123456/
   └─ 인물_14시03분12초_123456_local_3/
      ├─ clip.mp4
      ├─ crop.jpg
      └─ trajectory.jpg
```

- 저장 위치가 설정되고 YOLO가 활성화된 경우 카메라별 ClipManager가 위 temp 경로를 사용한다. 날짜/실행 폴더는 Manager 시작 시각, 인물 폴더는 추적 시작 시각이다. 작업 폴더의 배타적 생성과 순번으로 동일 시각·동일 로컬 ID·재시작 자료를 분리한다. UUID는 내부 식별에만 사용한다.
- `clip.mp4`는 기존 전체 화면 클립이며 10초/30초/전체 설정을 유지한다. Writer를 닫은 뒤에만 완료 경로를 알린다. 클립 종료 후에도 궤적 수집을 계속하고, 인물 유실·STOP·추적 세대 초기화 시 마지막 프레임에 궤적을 그려 `trajectory.jpg`를 저장한다.
- 대표 `crop.jpg`는 현재 유효한 관측의 OSNet용 5장 저장 결과 중 첫 이미지로 만든다. `output`의 5장을 보존하고 한 장만 temp 내부에 복제하며, 복제·파일명 확정 이후에 완료 경로를 알린다. VLM crop에 의존하지 않는다. 5장을 모으지 못했거나 종료/초기화/STOP으로 결과가 무효가 된 관측은 대표 crop이 없을 수 있다.
- `ClipManager.on_update` → `VideoWorker.media_ready`는 완료 파일 경로와 카메라/실행/추적 세대/로컬 ID, 최초·마지막 관측 시각, crop 작업 ID를 포함한 불변 `PersonMediaUpdate`를 전달한다. 완료 전 파일 경로는 `None`이며 프레임은 전달하지 않는다. `finished_at`은 추적이 종료된 관측의 마지막 탐지 시각이다. 각 자료는 서로 다른 순서로 완료될 수 있다.
- 완료 상태는 메모리 알림이며 재시작 복구용 영속 기록은 아니다. 추적 종료 후 영상 프레임·궤적 점을 가진 활성 상태는 제거한다. 2단계 당시에는 파일을 temp에 보존했으며, 현재 3단계는 확정 글로벌 ID가 있는 자료의 최종 이동을 연결했다.
- 대표 crop 복제/파일명 확정 실패는 완료로 알리지 않고 오류를 표시하며, OSNet 원본과 기존 ReID 입력을 유지한다. 자동 재복제는 하지 않는다. 클립/궤적 실패는 기존 영상 오류·정리 실패 처리를 따른다. 실패한 파일·부분 파일을 자동 삭제하지 않는다.

현재는 각 `VideoWorker`가 `workers/crop_worker.py`의 **독립적인 CropWorker 스레드와 제한 큐**를 소유한다. `storage/crop_collector.py`의 후보 관리·JPEG 저장은 CropWorker 안에서만 실행한다. 이전 동기 수집 구조는 아래 2026-11-15 기록에 남겨 두었다. OSNet·글로벌 ID·이벤트·DB/API 연동은 추가하지 않았다.

```text
카메라 → VideoWorker (영상 수신·YOLO·ByteTrack)
             → 인물별 0.5초 간격 crop 복사 → 제한 큐(16개)
                 → CropWorker (기존 전신 판정·크기·선명도 검사)
                     → CropCollector (첫 유효 5장 수집·저장)
```

- **FullBodyChecker 코드와 기본값은 그대로 유지**한다. 원본 bbox와 프레임 크기로 전신 판정을 통과해야 수집한다. 현재 기본값은 프레임 높이 대비 bbox 높이 45% 이상, 화면 가장자리 여백 10px이다. 기존 FULL/PARTIAL 화면 표시도 유지한다.
- 전신 조건에 추가로 crop 너비 64px·높이 128px 이상, Laplacian 분산 50 이상을 적용한다. 후보끼리 순위를 비교하거나 교체하지 않고 통과한 첫 5장을 저장한다.
- 간격은 CropWorker의 처리 시각이 아니라 VideoWorker에서의 제출 시각으로 제한한다. 박스·글자를 그리기 전 bbox 복사본에 원본 bbox·프레임 크기·촬영 시각·추적 세대를 함께 전달한다. 실행별 CropWorker 객체가 분리되어 있다.
- 큐에는 최대 16개의 crop이 대기한다. 가득 차면 새 후보를 건너뛰며 큐 공간이나 평가·저장 완료를 기다리지 않는다. 이미지 복사와 짧은 상태 잠금은 VideoWorker에 남아 있으며 CPU·디스크 경합까지 없어지는 것은 아니다.
- 저장 완료·실패 상태를 생산자와 공유하여 해당 추적 대상의 추가 제출을 중단한다. 결과는 별도 결과 큐에서 VideoWorker가 확인하여 기존 콘솔 완료 메시지·오류 신호로 전달한다. 후보 이미지와 Collector 상태는 CropWorker만 수정한다.
- 추적 종료는 해당 대상을 무효화하고, 추적 세대 변경은 대기 작업을 폐기한다. 무효화된 작업은 후보로 반영하지 않는다. STOP/AI 비활성화 시 신규 제출·대기 작업을 중단한다. 이미 처리·저장 중인 작업은 끝날 수 있다. VideoWorker 정리 시 CropWorker 종료까지 확인하며 GUI 스레드에서 join하지 않는다.
- 저장 위치는 프로젝트 루트 `output/camera_<ID>/날짜/person_<로컬ID>_<시각>/crop_01.jpg`~`crop_05.jpg`로 동일하다. 이름의 날짜·시각은 생산자에서 처음 관측한 시점이다. 원본 녹화·클립·궤적 경로, 레거시 VLM 경로는 변경하지 않았다.

```text
로그인 성공 → API 카메라 목록 조회 → 카메라 선택·등록·수정
  → START 전 최신 상세 확인 → 최대 두 대 실행
  → 전체 보기(4분할) / 개별 보기 전환 → 선택 카메라만 STOP
로그아웃 → 작업 정리 → 서버 세션 폐기·로컬 토큰 삭제 → 로그인 화면
프로그램 닫기 → 작업 정리 → 로그아웃 → 소유한 백엔드 종료 → 앱 종료
```

- 로그인·회원가입은 기존 남색 배경, 패널, 글꼴, 입력창과 버튼 테마를 사용한다.
- 아이디·비밀번호는 각각 최소 4자이며 회원가입 시 비밀번호 확인이 일치해야 한다. 서버에서도 같은 규칙을 검증한다.
- 가입은 자동 로그인이 아니다. 회원가입 성공 후 비밀번호를 지우고 로그인 화면으로 이동한다.
- 이미 계정이 생성된 경우의 `SIGNUP_CLOSED`는 로그인 화면으로 안내한다.
- 관제 창과 영상 작업은 로그인 전에 생성하지 않는다. 선택한 활성 카메라에 대해서만 START를 허용하고 실행 전 상세 API로 다시 확인한다.
- 카메라 등록 정보는 API로 DB에 저장한다. 분석·저장 옵션은 기존처럼 창의 메모리에 있으며 로그아웃 후 기본값을 사용한다. 이 옵션들의 영구 저장은 이번 범위에 포함하지 않는다.

## 인증과 HTTP

- [통합 API 명세서](docs/API_SPEC.md)의 인증 API 5개와 카메라 관리 API 4개를 호출한다. UI를 위한 API나 DB 테이블을 추가하지 않았다.
- HTTP는 `QNetworkAccessManager`의 비동기 요청으로 처리하며 기본 요청 제한 시간은 10초다. 리다이렉트로 자격증명을 다른 주소에 자동 전송하지 않는다.
- 중복 요청을 막고, 요청 중 입력·버튼을 비활성화한다. 비밀번호와 토큰을 화면·로그·파일에 출력하지 않는다.
- 토큰은 메모리에만 보관한다. 프로그램을 새로 실행하면 로그인해야 한다.
- 서버가 알려준 Access 만료 약 30초 전에 갱신한다. 만료가 임박하면 최소 1초 간격으로 조정한다.
- 갱신 후 Refresh 값을 교체하되 최초 로그인 기준 최대 8시간을 연장하지 않는다. 로컬 시간 관리는 단조 증가 시계를 사용한다.
- 일시적 갱신 네트워크 장애는 10초 후 재시도한다. 401·유효하지 않은 응답·최대 세션 시간 초과 시 관제 작업을 정리하고 재로그인을 요구한다.
- 로그아웃은 진행 중인 로그인·갱신 응답을 기다려 최신 Refresh 토큰으로 요청한다. 늦게 도착한 응답이 로그인 상태를 되살리지 않는다.
- 서버 로그아웃 확인에 실패해도 로컬 토큰은 삭제한다. 이때 서버 세션 폐기는 확인되지 않았다는 안내를 남긴다.

## 작업 정리와 제한

- 로그아웃·창 닫기 중에는 START·설정 등 새 작업을 차단한다. GUI에서 `wait()`로 스레드 종료를 기다리지 않는다.
- 영상 루프는 예외가 발생해도 녹화·클립 정리와 스트림 해제를 시도한다. RTSP·VLM·복구 작업의 실제 종료까지 확인한 뒤 다음 화면으로 이동한다.
- VLM 추론·모델 로딩은 강제 중단하지 않는다. 실행 중인 분석 스레드가 끝나기 전에 모델을 해제하지 않는다. 대기 중 분석은 새로 시작하지 않는다.
- 리소스 모니터 타이머와 요청도 종료한다. 열린 설정 창도 닫는다.
- 30초 이상 지연되면 대기 안내를 표시하며 GUI는 계속 응답한다. 분석·드라이버·복구 요청이 반환하지 않으면 정리 대기가 계속될 수 있다. 작업 스레드를 강제 종료하거나 종료 성공으로 간주하지 않는다.
- 정리 중 예외를 확인하면 화면 전환을 차단하고 실패 안내를 표시한다. 실제 디스크 오류의 복구 기능은 추가하지 않았다.
- 백엔드는 로그아웃 시 유지한다. 프로그램 종료 시 stdin으로 정상 종료를 요청하고, 10초 내 종료되지 않을 때만 자신이 만든 자식 프로세스를 종료한다. 강제 종료 이력은 다음 서버 실행에서 `interrupted`로 정리된다.

## PyQt 카메라 관리 1단계 (2026-10-07)

- `ui/gui.py`: API 목록과 선택 ID, 빈 목록·조회 실패 구분, 비활성 카메라 표시, 저장 후 선택·목록 갱신을 구현했다. 목록 새로고침 시 존재하는 선택을 유지한다. 조회 실패 시 기존 목록을 보존하고 실패 안내를 표시한다.

- `app_controller.py`: 로그인 성공 후 기존 세션을 관제 화면에 연결한다. 로그아웃·종료 시 기존 Worker 정리 순서를 유지하고 카메라 요청을 취소한다.

### 2026-10-07 당시 실행 정책 (현재 정책은 아래 2단계 안내)

- START는 활성 카메라 선택 후 가능하다. 실행 전 상세 API에서 최신 장치 번호·RTSP 주소·사용 여부를 확인하며 조회 실패·비활성 상태에서는 실행하지 않는다.
- 한 번에 한 카메라만 실행한다. 실행·상세 조회·중지 처리 중에는 선택과 설정 변경을 막는다. 모니터링 창이 열려 있을 때도 카메라 전환 전에 창을 닫도록 한다.
- 대기 중은 등록 정보에 대한 표시이며 연결 성공이 아니다. LIVE는 프레임 도착으로 표시한다. AI 실패로 일반 CCTV 모드가 되어도 영상 연결 상태는 유지한다. 장애 구간 파일 복구 완료는 LIVE 상태를 직접 변경하지 않는다.
- STOP은 진행 중 상세 요청 취소, Worker 종료 요청, 녹화·VLM·복구·모니터링 종료 확인 순으로 처리한다. 실행 세대 번호로 늦은 프레임·이벤트를 무시한다. 정리 실패 시 재실행·전환을 막는다.

- `ui/resource_monitor_window.py`: 등록한 장치 API 주소의 `/monitor/resources`를 사용한다. 주소 미등록 시 장치 조회를 하지 않고 로컬 PC 리소스만 표시한다. 실행 중에는 시작 시 확정한 카메라 설정을 사용한다.
- 웹캠 프레임 수신 실패는 무한 오류 카드 반복 대신 Worker를 종료하며, 장치를 확인한 뒤 START로 재시도한다. RTSP는 기존 재연결을 유지한다.
- `video/video_stream.py`, `video/rtsp_receiver.py`: rtsps도 RTSP 수신기로 분류한다. 명시된 포트만 TCP 사전 확인하며, 포트 생략 시 8554를 임의로 가정하지 않고 OpenCV/FFmpeg 기본값에 맡긴다. IPv6 명시 주소도 TCP 확인 가능하다. 재연결 시 이전 프레임을 비우며 원본 RTSP URL 출력은 제거했다.

### 새 저장물 위치

```text
선택한 AI_CCTV 저장 경로/
  cameras/camera_<DB ID>/<실행별 UUID>/
    crops/
    원본 녹화본/
    이벤트 CLIP/
    복구 영상/
```

기존 저장 파일은 이동·삭제하지 않는다. 녹화와 복구는 같은 실행 폴더를 사용한다. 저장 경로 미설정 시 녹화·복구는 하지 않으며 기존 분석용 crop은 실행 위치와 무관한 `client_code/outputs/cameras/camera_<ID>/<UUID>/crops` 아래에 저장한다. UUID는 로컬 파일 격리용이며 향후 이벤트 API의 tracking_run_id를 대신하지 않는다.

- 실제 장치 확인 순서: 카메라 등록 → 저장 경로 설정 → 분석 OFF로 START/STOP 및 저장 확인 → 분석 ON 확인 → RTSP 장애·재연결 및 복구 확인 → 로그아웃·종료 후 장치 해제 확인.
- 다음 범위는 실제 장치 검증과 필요 시 보완이다. 다중 카메라 동시 실행, Flutter 송출, 이벤트 API·CNN/OSNet 교체는 이번 작업에 포함하지 않았다.


## 다중카메라 계획 1단계: 실행 관리자 분리 (2026-10-08)

- `CCTVMainWindow.runtime`의 `CameraRuntimeManager`가 상세 조회, 시작 시 설정 복사, Worker 생성·신호 연결, 연결 상태, 실행 세대 번호, STOP 타이머와 종료 확인을 소유한다. GUI의 기존 `worker` 호환 필드는 남기지 않았다.

- 검증: 클라이언트 전체 45개 테스트 통과(기존 36개 + 관리자 경계 7개 + 세션 종료 회귀 2개). 중복 시작, 설정 복사, 잘못된 상세, 생성 실패, 취소·재시작 이후 늦은 신호, 모니터 대기, 정리 실패, 세션 만료·로그아웃 순서를 확인했다. 기존 임시 백엔드 HTTP와 합성 영상 OpenCV 검증도 포함한다.

## 다중카메라 계획 2단계: 두 실행과 전체/개별 보기 (2026-10-08)

### 사용 방법과 실행 정책

1. 로그인 후 카메라를 선택하고 START한다. 다른 카메라를 선택해 START하면 최대 두 대가 실행된다. 등록 개수는 제한하지 않는다.
2. 왼쪽 `전체 보기`는 2×2 네 칸을 표시한다. 최대 두 칸에서 카메라를 실행하고 나머지는 `미사용`이다. 전체 보기에서는 START/STOP·모니터를 사용할 수 없다.
3. 카메라 선택은 표시만 바꾼다. 숨겨진 카메라의 Worker와 저장은 계속되며 실행 ID·저장 폴더는 유지된다. STOP은 선택한 카메라만 정리한다.
4. 상세 조회·연결 준비·재연결·정리 중에도 슬롯을 점유한다. 중복 START·세 번째 START는 관리자에서도 차단한다. 실패한 조회는 예약을 반환하고 정리 실패는 해당 슬롯을 유지한다.
5. 설정·카메라 관리·목록 새로고침은 모든 실행·상세 요청·모니터가 정리된 상태에서 허용한다. 실행 중에도 목록 선택과 다른 카메라의 STOP은 가능하다.
6. 모니터는 한 창이며 열 때의 카메라에 고정된다. 다른 카메라를 선택해도 대상은 바뀌지 않는다. 대상 STOP은 모니터 종료까지 기다리고 다른 카메라 STOP은 기다리지 않는다.
7. 이벤트 타임라인·인물 이벤트 카드·출현/사라짐/누적 집계는 제거했다. 카메라별 현재 탐지 인원과 연결·오류 안내는 유지한다. VLM은 OFF다. 이벤트 표시 제거는 기존 Worker의 인물 정리·클립·궤적 중단을 의미하지 않는다.

### 구조와 검증

- `CameraRuntimeManager.runs[camera_id]`가 요청·설정 복사·Worker·실행 세대·정리 상태를 보관한다. 카메라마다 별도 CameraApiClient를 만들고 같은 SessionManager의 갱신을 공유한다. 이전 실행 객체의 늦은 응답·신호는 무시한다.
- `CameraView`가 카메라별 최신 표시 이미지를 소유한다. GUI 스레드에서 이미지 사본을 만들고 종횡비를 유지하며, 동일 위젯을 전체/개별 보기에서 재배치한다. 연결 대기·장애·중지 상태에서는 이전 LIVE 프레임을 지운다.
- 전체 클라이언트 테스트 54개 통과. 두 슬롯 예약·취소·실패·개별 정리·재시작, 위젯 재사용·카메라별 프레임/통계, 모니터 격리, 두 Worker 종료 후 로그아웃, 실제 HTTP 동시 상세 조회의 단일 토큰 갱신을 검증했다.
- `tests/test_multi_camera.py`는 두 임시 MJPEG 영상을 실제 OpenCV로 읽고 AI OFF로 동시에 저장한다. 숨겨진 입력의 계속 처리, 한 대 STOP·재시작 중 다른 입력 유지, 실행별 MP4 재생 가능 여부와 전체 정리를 확인한다. 유한 합성 파일의 수신 속도를 테스트용으로 조절하며 실제 장치 FPS·녹화 품질 측정은 아니다.
- 4분할·개별 보기·크기 변경 자동 검증과 Windows Qt 렌더러의 합성 화면 배치를 확인했다. 사용자 장치에서 직접 조작한 검증과 구분한다.
- 기존 실행 명령과 의존성은 동일하다. 백엔드 코드·DB·API 계약을 변경하지 않았다.

### 2단계 완료 당시 남은 범위

3단계의 YOLO 동시 실행·추적 상태·인물 클립/궤적 격리 검증, 단선 중 인물 유실 정리, 저장 실패 전달 보완은 진행하지 않았다. 실제 웹캠·RTSP·GPU 성능·단선 복구도 미검증이다. 장치에서 우선 설정의 YOLO를 끄고 두 카메라 START → 전체/개별 보기 → 개별 STOP·재시작 → 로그아웃 순서로 확인한다.

## 다중카메라 계획 3단계: 추적 격리·저장·유실 처리 (2026-10-08)

### 구현

- Worker별 YOLO 모델·인물 상태·저장 관리자를 유지한다. 설치된 Ultralytics 8.4.77의 ByteTrack은 전역 ID 카운터를 생성/초기화 시 공유하므로 `detection/isolated_byte_tracker.py`에서 ID 발급만 인스턴스별로 격리했다. 매칭·칼만 필터 등 기존 ByteTrack 알고리즘은 그대로 사용한다. `PersonTracker`의 시작 콜백으로 해당 모델에만 연결하며 라이브러리 전역 변경은 하지 않는다.
- 프레임이 없어도 기존 3초 유실 기준으로 인물 상태·ID 연결을 제거하고 클립·궤적을 마무리한다. 새 프레임의 추적 전에 만료를 확인하므로 오래된 raw ID가 돌아와도 종료된 관측을 이어 쓰지 않는다. 3초 이상 추론 입력 공백 후에는 해당 ByteTrack 상태를 초기화하고 `tracking_generation`을 증가시킨다. 모델 재로딩 없이 로컬 ID 번호는 계속 증가한다. 한 프레임에서 두 인물에게 같은 보정 ID를 부여할 수 있던 오래된 raw ID 연결도 제거했다.
- 수신기가 연결 상태를 유지해도 3초 이상 새 프레임이 없으면 해당 카메라를 연결 대기로 표시한다. 현재 인원 표시·모니터 대상 고정은 2단계 구현을 유지한다. 새 프레임 없는 상태에서 탐지 인원을 임의로 생성하지 않는다.
- 원본 분할, 전체 프레임 `preview.mp4` 최대 길이, 클립 종료 후 궤적 수집, bbox 하단 중앙점·샘플링·평활화 정책은 유지한다. 원본 파일의 시작 시각에 마이크로초를 포함해 같은 초의 STOP/재연결 파일 충돌을 방지한다. 궤적은 JPEG 인코딩 후 파일로 기록하여 한글 경로와 쓰기 실패를 처리한다.
- Writer 열기, 파일 이름 변경, 궤적 인코딩·기록에서 확인한 실패를 숨기지 않는다. 영상 처리 중 저장 실패는 해당 Worker를 종료·정리하고 카메라별 오류로 안내한다. 한 클립의 종료 실패에도 나머지 인물 종료와 스트림 해제를 시도하며 마무리 실패는 `정리 실패`로 남긴다. 다른 카메라의 실행·STOP은 유지된다.
- 복구 요청의 예외도 카메라별로 안내하며 STOP 중 발생한 저장 실패는 정리 후에도 표시한다. 복구 ZIP은 실행 폴더의 `복구 영상`, 병합 MP4는 같은 실행 폴더의 `원본 녹화본`에 저장하는 기존 정책이다. 저장 루트 미설정 시 원본·클립·복구는 생성하지 않는다.
- 종료 시 Worker의 추적기 참조와 인물 상태를 해제한다. VLM OFF·이벤트 UI 제거를 유지하며 백엔드·API·DB·의존성 변경은 없다.

### 검증과 제한

- 클라이언트 전체 70개 테스트 통과(기존 54개 + 3단계 16개). 실행 명령은 위 검증 절과 동일하다. `git diff --check`도 통과했다.
- `tests/test_tracking_storage.py`: 실제 ByteTrack에 합성 탐지를 입력해 두 카메라의 생성·초기화에 따른 ID 격리를 확인했다. 모델은 가짜 YOLO로 대체하여 콜백 연결·긴 공백·ID 재등장·프레임 없는 유실 정리·저장 실패·종료 실패·저장 미설정 조건을 검증했다.
- `tests/test_multi_camera.py`: 두 합성 영상을 실제 OpenCV로 읽고 가짜 모델로 각각 두 인물을 반환했다. 같은 로컬 ID의 원본·클립·궤적 분리, 숨겨진 영상 처리, 개별 STOP·재시작, 모든 MP4 재읽기와 JPEG 디코딩을 확인했다. 기존 AI OFF·현재 인원·모니터·인증·종료 회귀도 통과했다.
- 복구 테스트는 가짜 HTTP 응답의 ZIP 저장·압축 해제와 병합 대상 경로를 확인하며 FFmpeg 병합 호출은 대체했다. 실제 장치 복구 API·실제 TS 병합 성공을 의미하지 않는다.
- 실제 YOLO 가중치 추론, 웹캠·RTSP, GPU 동시 실행·장시간 메모리·처리 성능은 실행하지 않았다. OpenCV가 반환값/예외 없이 내부에서 놓치는 디스크·인코더 오류나 물리 디스크 내구성을 보장하지 않는다. ByteTrack 연결은 설치된 8.4.77로 검증했으므로 라이브러리 변경 시 관련 테스트를 다시 실행한다.
- 다음 단계는 별도 요청 후 진행할 4단계 실제 장치·성능 검증이다. crop 정책·새 이벤트·OSNet·CNN·Flutter 송출은 추가하지 않았다.

## 다중카메라 계획 4단계: 실제 장치·성능 부분 검증 (2026-10-08)

- 실제 웹캠 1280×720: AI OFF 16.53 FPS, 최초 AI ON 8.80 FPS. 재시작 AI ON은 15.94/7.56 FPS로 변동했다. 실제 YOLO26s는 RTX 3050 Laptop GPU의 `cuda:0`에서 실행됐다. 뒤의 웹캠 시험에서는 인물 클립·궤적도 생성·재읽기했다.
- 같은 웹캠 녹화본의 보조 비교: 한 모델 ON 22.62 FPS, 두 입력 OFF 각각 23.80 FPS, 두 모델 ON 각각 16.37/16.32 FPS. **로컬 재생 결과를 실제 두 장치나 네트워크 처리 성능으로 해석하지 않는다.**
- 두 모델 세 차례, 실제 웹캠 두 차례의 동일 프로세스 재시작과 정상 정리를 확인했다. 종료 후 CUDA 할당은 각각 64 MiB/32 MiB로 반복 사이 유지됐지만 짧은 관측이며 장시간 누수 검증은 아니다.
- 실측에서 생성한 MP4 51개와 궤적 JPEG 12개를 읽었고 저장 오류는 없었다. 최초 AI 실행의 원본 10초 구간이 약 7.17초로 재생되는 한계도 확인했다. 디코딩 성공을 무손실 녹화로 설명하지 않는다.
- 목표는 버벅임 최소화·통신 지연 2초 미만이다. 실제 엣지노드·네트워크·촬영 시각 계측이 없어 지연 목표는 판정할 수 없으며 실제 두 장치·단선/복구·관제 창 조작·장시간 검증은 남아 있다. **4단계 전체 완료가 아니다.**
- 수동 측정은 `tests/manual_multi_camera_probe.py`, 원자료는 `outputs/stage4/`, 환경·측정 정의·제한·명령은 [4단계 실측 기록](docs/MULTI_CAMERA_STAGE4_VALIDATION.md)에 있다. 진단 스크립트 외 제품 처리 코드·DB·API·의존성은 변경하지 않았다.
