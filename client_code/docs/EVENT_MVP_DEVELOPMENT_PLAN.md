# 이벤트 MVP 개발 계획

- 기준일: 2026-11-19. 현재 **1~5단계 완료**다. 5단계는 합성 전체 흐름·단일 웹캠 정상 시나리오 범위이며 다중 카메라/RTSP/장시간 검증 완료를 뜻하지 않는다.
- 이벤트 개발·검증·다음 단계 착수 전에 이 문서, BACKEND_SCHEMA.md의 events 절, API_SPEC.md의 이벤트 절을 읽는다.
- 소유 계약: [DB 스키마](BACKEND_SCHEMA.md), [API 명세](API_SPEC.md#이벤트-api--pc-이벤트-mvp).
- 각 단계는 사용자가 지정하면 진행한다. 커밋·푸시·브랜치 변경·운영 DB 초기화는 수행하지 않는다.

## 1. 목표와 범위

PC에서 이벤트를 판단하고 별도 공용 이벤트 저장 큐/작업 스레드로 백엔드에 저장한다. DB 이력·미디어 경로를 API로 조회하는 단계까지다. PyQt 이벤트 목록/상세 화면·Flutter·알림/푸시·연결 오류/CNN 이벤트·미디어 파일 응답·정적 마운트·HTTP Range는 제외한다. 저장 경로 설정과 오류 안내를 위한 기존 UI 조정은 후속 연결 범위다.

ReID의 CropWorker → OSNetWorker → 공용 GlobalPersonManager → 글로벌 인물 API 저장 확인 → 영상 표시 흐름은 유지한다. 이벤트 저장 큐는 ReID 큐와 별개이며 이벤트 API 응답을 기존 ReID 처리의 선행 조건으로 만들지 않는다. 1단계는 이 큐나 영상 연결을 구현하지 않는다.

## 2. 발생 기준

| 종류 | 발생 조건 | occurred_at |
| --- | --- | --- |
| person_appeared | 현재 관측의 글로벌 ID 확정 | 첫 탐지 시각 |
| person_disappeared | 정상 영상 수신 중 약 3초간 미탐지 | 마지막 탐지 시각 |
| camera_started | 실행 UUID별 첫 프레임 수신 성공 1회 | 첫 프레임 수신 시각 |
| camera_stopped | 첫 프레임을 받은 실행의 사용자 STOP/정상 종료 정리 성공 | 정리 완료 시각 |

- 시작 실패·강제 종료·오류 종료·정리 실패는 정상 중지로 기록하지 않는다. 재연결은 새 시작이 아니다.
- STOP·영상 끊김·추적기 초기화는 인물 사라짐으로 기록하지 않는다. 미디어 마무리·기존 등장의 경로 갱신은 계속한다.
- 글로벌 ID 미확정 관측은 등장·사라짐 모두 제외하며 temp 자료를 보존한다. 모든 탐지 인물이 DB에 남는 것은 아니다.
- PersonMediaUpdate.finished_at은 정리에서도 생기므로 사라짐의 근거로 쓰지 않는다. 자연 유실 여부와 마지막 탐지 시각은 종료 전 확보한다.

## 3. 관측·순서·실패 경계

- DB 관측 키: 서버 실행 + 카메라 + 카메라 실행 UUID + 추적 세대 + 로컬 ID. 등장/사라짐을 각각 한 행으로 제한한다. 카메라 이벤트 키는 인물 필드 없이 실행과 종류로 구분한다.
- 현재 StablePersonIdMapper의 번호는 증가하며 종료된 로컬 ID를 재사용하지 않는다. 이를 검증·유지한다. 향후 같은 실행/세대에서 재사용하는 구현으로 바꾸면 관측 키도 재논의해야 한다.
- PC 내부는 기존 crop 작업 UUID도 검증한다. 늦은 결과를 다른 관측에 연결하지 않으며 DB에 UUID 컬럼을 추가하지 않는다. 카메라 UUID는 기존 hex 입력도 받고 저장/응답은 하이픈이 있는 UUID v4로 정규화한다.
- 동일 키·동일 불변 내용 재요청은 기존 행과 현재 미디어를 반환한다. 같은 키에 다른 발생 시각/글로벌 ID/관련 이벤트이면 충돌이다. 생성 재요청의 미디어는 기존 경로를 덮어쓰지 않는다. 경로 변경은 PATCH만 사용한다.
- 같은 관측의 등장 생성 성공 확인 → 미디어 PATCH/사라짐 등록 순서를 지킨다. 응답 유실은 같은 키로 제한 재시도한다. 이전 경로 PATCH가 최종 경로를 덮어쓰지 않도록 순차 처리한다.
- 정상 종료/로그아웃은 영상·미디어 정리 → 저장 큐 제한 시간 마무리 → 인증 폐기 → 백엔드 종료 순서다. runtime_manager의 UI 필터와 별도로 종료 중 마지막 미디어 알림을 소비해야 한다. 3단계 큐 대기 상한 128개/결과 상한 256개, HTTP 연결 1초·읽기 2초, 동일 본문 최대 2회 시도, 영상 정리 후 이벤트 마무리 8초를 적용했다. 4단계에서 관측별 생성 확인 후 미디어/사라짐 의존 처리를 연결했다.
- 영속 outbox·무한 재시도·자동 복구는 추가하지 않는다. 저장 실패는 안내하고 성공으로 표시하지 않는다. 재로그인/새 서버 실행 뒤 과거 미확정 작업을 자동 재전송하지 않는다.

## 4. 파일·저장소 계약

기존 저장 구조를 유지한다. OSNet용 첫 5장은 프로젝트 output에 보존하며 대표 crop을 위해 이동/삭제하지 않는다. 작성 중 파일은 프로젝트 temp, 완료 파일은 같은 볼륨의 사용자 AI_CCTV 아래로 os.rename한다. 다른 볼륨 자동 복사는 없다.

```text
선택 위치/AI_CCTV/
├─ 원본 녹화본/YYYY-MM-DD/camera_ID/시작시각~종료시각.mp4
└─ 이벤트/person_ID/YYYY-MM-DD/camera_ID/시작시각~마지막관측시각/
   ├─ clip.mp4
   ├─ crop.jpg
   └─ trajectory.jpg
```

- 파일 작성 완료 → 최종 위치 이동 성공 → DB 상대 경로 갱신 순서다. 추적 중에는 시작 시각 폴더를 사용하고 종료 시 폴더명을 확정한다. 완료 경로는 최종 이름 변경 전에도 유효하며 변경 후 세 경로를 한 PATCH로 갱신한다.
- PersonMediaUpdate 경로는 temp/최종 위치가 혼합될 수 있다. move_failed가 true여도 이미 이동된 다른 파일은 등록 가능하므로 파일별로 기준 경로 아래 이동 완료 자료인지 판단한다. temp 경로를 저장하지 않는다.
- NULL은 이용 불가능을 뜻한다. 실패 상세 상태·추가 테이블은 없다. 미디어는 등장에만 모으고 사라짐은 related_event_id로 연결한다.
- 저장소 기준 절대 경로는 백엔드 설정 파일에서 유지한다. 이벤트 저장 전에 설정을 완료하고 첫 이벤트 커밋 이후 다른 경로로 변경하지 못하게 한다. 서버 재실행도 DB의 이벤트 존재 여부로 제한을 유지한다. 동일 경로 재설정은 허용한다.
- GUI는 백엔드 설정을 조회·확인한 경로로 작업해야 한다. 활성 촬영 중 경로 변경도 막아 서로 다른 기준을 사용하지 않게 한다. 2단계에서 설정 저장의 원자성·이벤트 생성과의 경합·실제 경로/심볼릭 링크 검증을 구현했다. 3단계에서 GUI 경로 동기화와 활성 촬영 중 변경 차단도 연결했다.
- 저장 폴더명은 기존 로컬 시각을 유지한다. 이벤트용 첫/마지막 탐지 시각은 UTC aware로 전달한다. ReID observed_at은 첫 품질 통과 crop 시각이므로 등장 시각으로 대체하지 않는다.

## 7. 2단계 구현·검증 기록

- 추가: backend/routers/events.py, routers/settings.py, schemas/storage.py, services/storage_service.py, tests/test_event_api.py. main.py/dependencies.py에서 Service·Router·인증을 연결했다. 이벤트 4개 API와 저장소 GET/PUT 2개를 제공한다.
- 저장소 설정은 DB 옆 ai_cctv.storage.json에 저장한다. 기본 경로는 client_code/backend/data/ai_cctv.storage.json이다. 별도 테이블은 없으며 create_app(db_path, storage_config_path)로 임시 파일을 주입할 수 있다. 설정이 없으면 GET은 null/locked=false, 첫 이벤트 POST는 409다.
- 이미 존재하는 AI_CCTV 디렉터리, 프로젝트와 같은 볼륨, 프로젝트 temp/output 하위 제외를 확인한다. 실제 절대 경로로 정규화하고 기존 파일을 이동/삭제하거나 미디어 폴더를 생성하지 않는다. 설정 파일은 같은 디렉터리 임시 파일 flush/fsync·닫기 후 os.replace한다. 교체 실패 시 이전 파일/메모리 설정을 유지한다.
- 설정 변경과 이벤트 생성/미디어 갱신은 하나의 StorageService RLock → SQLite BEGIN IMMEDIATE 순서로 보호한다. 이벤트가 검증을 마치고 커밋하기 전 설정 변경이 끼어들 수 없다. 첫 성공 커밋 이후 카메라 이벤트를 포함해 모든 이벤트가 경로를 잠근다. 같은 정규 경로는 허용하며 롤백은 잠금을 남기지 않는다.
- 상대 경로 문법에 Windows 예약 장치 이름과 SQLite 정수 범위 검증을 보강했다. 미디어는 기존 6항목 이벤트 폴더 구조, 등장 행의 인물/카메라, 날짜/파일명 일치, 실제 0바이트가 아닌 일반 파일을 확인한다. 하위 링크/Windows junction/reparse point는 저장소 내부를 가리켜도 거부한다. 갱신 후 남는 미디어는 모두 같은 관측 폴더여야 하므로 폴더명 변경 시 모든 현재 경로를 한 요청으로 보낸다.
- 동일 생성 재요청은 이미 이동/이름 변경되어 없어진 최초 경로를 다시 검증하지 않고 현재 DTO를 반환한다. 최초 응답 유실 후 재시도가 최신 경로를 덮어쓰지 않는 것을 확인했다. 미디어 PATCH 실패 시 기존 필드 전체를 유지한다.

### 인물 발생과 파일 알림

- ClipManager의 기존 저장 구조·완료 파일 rename·미확정/실패 temp 보존·OSNet 첫 5장 보존 정책을 유지했다. PersonMediaUpdate에 최초/마지막 관측 UTC 시각, 종료 사유, 단조 증가 revision을 덧붙였다. 기존 로컬 시각 필드는 폴더 이름에 유지하고 이벤트는 첫 탐지 UTC 시각을 사용한다. ReID의 첫 품질 통과 crop 시각으로 대체하지 않는다.
- save_representative_crop에서 작업 UUID를 연결하고 기존 assign_global_person이 카메라/실행/세대/로컬 ID/작업 UUID를 검증한 뒤 글로벌 ID를 연결한다. 그 스냅샷으로 등장 이벤트를 제출한다. 영상 표시·ReID 저장 판단은 이벤트 응답을 기다리지 않는다.
- 자연 유실만 finish_reason=natural이다. 프레임 실패/긴 수신 공백은 stream_gap, 추적 세대 변경은 tracking_reset, STOP/종료/분석 정리는 cleanup으로 마무리하며 사라짐을 만들지 않는다. finished_at 유무만으로 사라짐을 판단하지 않는다.
- 정상 프레임 처리 뒤 미탐지 만료만 자연 유실로 처리한다. 수신 실패/긴 공백 중에도 기존 클립/궤적은 정리하지만 자연 유실 신호를 만들지 않는다. 세대 변경은 기존 미디어를 마무리하고 PersonStateManager의 옛 탐지 상태도 지운다.
- VideoWorker는 글로벌 ID·crop 작업 ID가 있는 최신 메타데이터를 관측별로 합쳐 최대 128개 버퍼에 보존한다. 프레임/궤적 점/벡터는 넣지 않는다. runtime_manager는 media_ready를 UI 중지 필터와 별도로 처리하고 Worker 종료/실행 해제 전 버퍼를 다시 수집한다. 따라서 종료 중 마지막 폴더명/경로 알림이 UI 필터로 사라지지 않는다. 버퍼 초과는 저장 미확인으로 안내한다.

### API 순서와 늦은 결과

- EventCoordinator는 실행별 등록과 카메라/실행 UUID/세대/로컬 ID, 불변 crop 작업 UUID/글로벌 ID/최초 시각을 확인한다. 같은 관측의 오래된 revision·다른 작업/글로벌 ID는 무시한다. 완료한 최근 256개 키를 중복 차단에 보존하며 활성/저장 대기 관측은 128개로 제한한다. 실행 해제 이후 외부 스냅샷은 받지 않고 이미 접수된 후속 저장만 마무리한다.
- 관측당 HTTP 작업 하나만 진행한다. 등장 POST 성공으로 event_id 확인 → 최신 미디어 PATCH → 자연 유실 사라짐 POST 순서다. 등장 생성 실패는 종속 요청을 보내지 않고 안내한다. 미디어만 실패한 경우 이미 저장된 등장을 참조해 사라짐을 저장할 수 있으며 미디어 실패는 별도로 안내한다.
- 각 스냅샷에서 사용자 AI_CCTV 기준 상대 경로가 되는 완료 파일만 선택한다. temp 경로는 NULL로 시작하고 전송하지 않는다. move_failed=true라도 이미 이동한 다른 파일 경로는 반영한다. 상세 파일 실패 상태는 새 컬럼에 저장하지 않는다.
- 개별 완료 PATCH는 이용 가능한 경로만 보내고 아직 없는 필드는 생략한다. 이전 요청이 응답 유실 후 늦게 처리되어도 뒤늦게 완성된 다른 파일을 NULL로 지우지 않는다. 폴더명 변경 후에는 이용 가능한 모든 최신 경로를 한 PATCH로 보낸다. 명시적 NULL 제거를 지원하는 기존 관리 API 계약은 유지하지만 PC 자동 갱신은 이를 이용하지 않는다.
- POST가 옛 폴더 경로 검증에 걸리면 불변 식별값/발생 시각을 유지한 채 미디어 없는 생성 재확인을 한 번만 한다. 이후 현재 경로를 PATCH한다. 정상 생성에서는 준비된 경로를 함께 보낸다. 재확인 POST도 거부되면 중단/안내하며 새 ID·새 관측으로 바꾸지 않는다.
- PATCH가 끝나기 전에 더 최신 스냅샷이 도착하면 완료 응답 이후 최신 경로를 반영한다. 옛 경로 거부 시 새 revision이 있으면 그 최신 경로만 보낸다. 같은 실패 revision은 반복하지 않는다. HTTP 전송 자체의 최대 2회 제한 재시도는 유지하며 영속 outbox·무한 재시도·재로그인 재전송은 없다.
- 정상 종료 시 영상/미디어 버퍼 수집 후 큐 마무리를 시작한다. 이미 접수된 등장의 응답 뒤에도 종속 PATCH/사라짐을 넣을 수 있게 HTTP 큐를 바로 닫지 않는다. 전체 대기 요청이 끝나면 닫고, 기존 8초 제한을 넘기면 저장 미확인 경고와 함께 중단한다. 진행 중인 서버 커밋의 강제 취소/되돌리기는 보장하지 않는다.
