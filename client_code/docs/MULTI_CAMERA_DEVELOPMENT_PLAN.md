## 2. 최종 목표와 합의 이력

### 2.1 최종 목표

같은 PyQt 관제 창에서 최대 두 카메라를 동시에 실행한다. 각 카메라의 영상 수신, YOLO26s 사람 검출·추적, 원본 녹화, 기존 인물별 클립·궤적 처리를 독립적으로 유지한다. 사용자는 왼쪽 목록의 `전체 보기`와 개별 카메라를 선택해 표시 방식만 전환한다.

### 2.2 이전 제안 중 최종 계획으로 대체된 내용

- 카메라는 최대 두 대다. 많은 카메라를 위한 공용 YOLO 큐·배치 추론 구조를 먼저 만들지 않는다.
- YOLO26s 객체는 카메라별 한 개로 시작한다. 같은 가중치 파일을 각 Worker에서 로딩하며, 별도 학습·모델 파일 복제는 필요하지 않다.
- 초기의 단순 좌우 2분할 제안은 **전체 보기 2×2 4분할 + 개별 보기**로 대체한다. 4분할은 화면 배치이며 동시 실행 한도는 여전히 두 대다.
- 전체 보기용 관제 창이나 별도 전체 보기 프로그램을 만들지 않는다. 같은 GUI와 영상 표시 구성 요소를 재사용한다.
- 카메라별 이벤트 목록 구현 제안은 철회한다. 이번에는 **기존 이벤트 UI와 출현·사라짐 집계를 비활성화**한다.
- VLM은 이번 단계에서 사용하지 않는 것으로 사용자가 명시적으로 선택했다. 이후 자체 CNN으로 교체한다. VLM 공유·최적화 작업을 하지 않는다.
- crop 정책, 새 이벤트 스키마, OSNet 글로벌 동일인 연결, CNN 분석은 후속 작업이다.

### 2.3 합의와 구현 제안의 구분

최대 두 대, 카메라별 YOLO, 동일 GUI의 전체/개별 보기, 4분할, 이벤트·VLM 비활성화, 기존 클립·궤적 정책 유지가 사용자 요구다.

이 문서의 구체적인 파일명, 전체 보기에서 START/STOP 비활성화, 모니터 한 창의 대상 고정, 현재 인원만 표시 등은 그 요구를 충족하기 위한 구현 기준안이다. 새로운 기능을 임의로 늘리지 않는 범위에서 실제 코드에 맞춰 조정할 수 있으며, 사용자 요구 자체를 바꾸는 선택은 이유와 영향을 설명한다.

## 4. 계획 작성 시점의 코드 구조와 용어

### 4.1 프로세스 경계

```text
main.py
  └─ AppController
       ├─ 인증·세션·화면 전환
       ├─ FastAPI 자식 프로세스 실행·종료 관리
       └─ CCTVMainWindow
            └─ VideoWorker 한 개
                 ├─ 영상 수신
                 ├─ YOLO 추적 / 선택적 VLM
                 └─ 파일 저장

PyQt ──HTTP──> FastAPI Router → Service → Repository → SQLite
카메라 ──영상──> PyQt의 VideoStream / VideoWorker
```

FastAPI는 계정·카메라 등록 정보·DB를 담당한다. 실제 영상·AI·파일 저장은 현재 PyQt 프로세스 안에서 처리한다. 백엔드에 PyQt·YOLO 모델을 import하거나 API 요청 안에서 무거운 영상 처리를 실행하지 않는다.

### 4.2 객체와 역할

| 이름 | 의미 |
| --- | --- |
| `self` | Python의 현재 객체. Java의 `this`에 해당 |
| `self.worker` | 현재 관제 창의 필드. `VideoWorker` 객체 하나를 참조하며 미실행 시 `None` |
| `VideoWorker` | `QThread`를 상속한 카메라 한 대의 처리 흐름 클래스 |
| `VideoWorker(...)` | 특정 카메라의 작업 객체 생성 |
| `worker.start()` | 작업 스레드 시작. 생성자 자체가 백그라운드에서 실행되는 것은 아님 |
| `VideoStream` | 웹캠·RTSP 입력의 open/read/release 공통 경계 |
| `RTSPReceiver` | RTSP 수신·연결 감시·재연결을 담당하는 내부 스레드 관리 |
| `PersonTracker` | YOLO 모델과 `track(persist=True)`, 로컬 ID 보정 |
| `PersonStateManager` | 카메라 내 인물별 상태·마지막 관측 시각·분석 상태 |
| `RecordingManager` | 원본 녹화 |
| `ClipManager` | 인물별 preview 클립·궤적 관리 |
| `CropManager` | 인물 이미지 저장. 현재 실행 조건이 VLM과 연결됨 |
| `VLMWorker` | 별도 큐·스레드의 이미지 분석. 이번 실행에서는 사용하지 않음 |
| `NetworkRecoveryManager` | 장치 API를 이용한 단선 구간 복구 |

현재 Worker 신호는 `frame_ready`, `metrics_ready`, `event_ready`, `loading_ready`, `status_ready`와 `finished`다. 화면은 신호를 받아 표시한다. Worker에서 직접 GUI 위젯을 수정하지 않는다.

### 4.3 실제 단일 카메라 제약

- `ui/gui.py`: `self.worker`, `running_camera`, `detail_pending`, `run_generation`, `_stopping` 등이 한 실행을 전제로 한다.
- 실행 중에는 카메라 선택·다른 START·설정 변경이 잠긴다.
- `_start_camera()`가 통계·이벤트 화면을 전체 초기화한다.
- `stop_video()`와 `_poll_stop()`이 영상 Worker와 모니터 종료를 함께 처리한다.
- `video_label` 하나에 영상을 표시하며 최소 크기 800×450을 사용한다.
- `CameraApiClient` 객체 하나는 진행 중 요청 하나를 관리한다.
- YOLO는 `VideoWorker._run_video()`에서 `PersonTracker(model_path="yolo26s.pt")`로 생성된다. 모델은 해당 Worker의 실행 흐름에서 생성·사용한다.
- 영상 읽기·원본 녹화·YOLO·클립·화면 전달이 같은 Worker 반복문에 있다. AI 부하는 영상 갱신과 저장 호출 주기에도 영향을 줄 수 있다.

## 5. 목표 구조와 책임

```text
AppController                       # 기존 앱 생명주기 유지
  └─ CCTVMainWindow                 # 사용자 조작·표시 모드·화면 배치
       ├─ 왼쪽: 전체 보기 / 카메라 목록
       ├─ 중앙: 동일 CameraView 재사용
       └─ CameraRuntimeManager      # 신규, 카메라 실행 관리
            ├─ camera_id A → 실행 정보 → VideoWorker A → YOLO26s A
            └─ camera_id B → 실행 정보 → VideoWorker B → YOLO26s B
```

### 5.1 CameraRuntimeManager

- GUI 스레드에서 실행 생명주기를 조정하는 QObject 기반 관리자를 우선 고려한다. 자체 추론 스레드는 필요 없다.
- 카메라별 실행 요청·상태·Worker·시작 시 설정 스냅샷·실행 식별 정보를 관리한다.
- 필요한 시작·정지·전체 종료·결과 전달 기능만 제공한다. 범용 기반 클래스나 플러그인 프레임워크를 만들지 않는다.
- 카메라별 상태에는 조회/연결 준비, 실행, 재연결, 중지 중, 중지, 오류·정리 실패를 구분한다.
- 연결 상태와 AI 사용 가능 상태를 구분한다. YOLO 실패 후 영상이 계속 나오면 연결을 끊긴 것으로 표시하지 않는다.

### 5.2 VideoWorker

- 카메라 한 대의 기존 처리 흐름을 유지한다.
- 모델·추적기·인물 상태·녹화·클립·복구 객체를 다른 카메라와 공유하지 않는다.
- YOLO 추적 API를 검출/추적으로 분해하지 않는다. `PersonTracker`를 우선 재사용한다.
- 종료 시 모델 참조와 하위 작업 정리를 확인한다. 다른 Worker가 쓰는 GPU 자원을 전역 초기화하는 조치를 추가하지 않는다.
- 두 모델을 같은 GPU에서 실행한다고 처리 성능이 두 배가 되는 것은 아니다. 모델 중복 메모리와 CPU/GPU 경쟁을 실측한다.

### 5.3 CameraView와 화면 데이터

- 한 카메라의 이름·영상·연결 상태를 표시하는 위젯을 추출한다.
- 전체/개별 보기는 위젯 재배치·표시 여부 변경으로 처리한다. 동일 카메라의 Worker나 수신기를 추가 생성하지 않는다.
- 선택은 표시 대상이고, 실행 여부는 관리자의 상태다. 둘을 혼용하지 않는다.
- 최신 프레임·탐지 인원 등 표시 데이터의 소유 위치를 명확히 하고 중복 캐시를 늘리지 않는다.
- QImage/QPixmap 변환과 위젯 갱신은 GUI 스레드에서 처리한다. 전달 프레임 버퍼의 수명·변경 가능성도 확인한다.

## 6. 화면과 제어 정책

### 6.1 전체 보기

- 왼쪽 목록 최상단에 `전체 보기` 항목을 둔다.
- 중앙에 2×2 네 칸을 표시한다. 최대 두 카메라가 영상을 표시하고 나머지는 `미사용` 등 명확한 빈 상태로 둔다.
- 두 카메라의 슬롯 배치는 안정적으로 유지한다. 한 카메라의 단선만으로 다른 카메라 영상 위치를 이동시키지 않는다.
- 연결 준비·재연결·중지 상태를 해당 카메라 칸에 표시한다. 이전 프레임을 정상 LIVE 영상처럼 방치하지 않는다.
- 초기에는 전체 보기에서 START/STOP을 비활성화하고 카메라 선택 후 제어하도록 안내한다. 전체 시작·정지 기능은 추가하지 않는다.
- 4분할을 4대 지원으로 설명하지 않는다.

### 6.2 개별 보기

- 카메라 목록을 누르면 해당 영상이 중앙 영역 전체를 사용한다.
- 실행 중 카메라 선택과 전체/개별 보기 전환을 허용한다.
- 보이지 않는 카메라의 YOLO·녹화·클립·궤적 처리는 계속된다.
- START/STOP은 선택 카메라에만 적용한다. 선택 변경은 실행을 시작하거나 중지하지 않는다.
- 전체/개별 보기 전환으로 추적 ID, 저장 폴더, 실행 UUID, 모델이 초기화되면 안 된다.
- 기존 800×450 최소 크기를 위젯 두 개에 그대로 적용하지 않는다. 창 크기에 맞게 종횡비를 유지하고 크기 변경 시 다시 맞춘다.

### 6.3 이벤트·통계·상태

- 이벤트 타임라인과 인물 이벤트 카드를 숨기고 그 공간을 영상 영역에 활용한다.
- 출현·사라짐 집계와 기존 이벤트 히스토리는 이번 UI에서 제외한다.
- 필요 최소 통계는 카메라별 현재 탐지 인원이다. 전체 인원을 동일인 중복 제거한 수처럼 합산·표현하지 않는다.
- 기존 `tracked_total`은 현재 인물 상태 수인데 UI는 `누적 추적`이라고 표시한다. 잘못된 누적 의미를 유지하거나 새로운 누적 통계를 구현하지 않는다.
- **`event_ready`를 단순히 전부 무시하지 않는다.** 현재 네트워크 장애·복구·AI 오류도 이 신호를 사용한다. 내부 상태 처리는 유지하고 이벤트 카드 생성만 중단한다. 필요하면 상태/오류 전달을 최소한으로 분리한다.
- 인물 사라짐 정리는 클립·궤적 마무리에 필요하므로 이벤트 UI 비활성화와 무관하게 유지한다.

### 6.4 설정·모니터

- 기존 공통 YOLO·저장 옵션을 사용하며 시작할 때 복사한다.
- 설정·카메라 등록 수정·목록 새로고침은 전체 작업과 시작 요청이 정리된 상태에서 허용하는 보수적인 정책을 유지한다. 카메라 선택은 실행 중에도 허용한다.
- VLM이 현재 기본값 True인 진입점도 확인하여 실제 Worker에 False가 전달되도록 한다. 옵션을 켤 수 있는 것처럼 표시하지 않는다. 기존 VLM 소스 삭제·CNN 대체는 이번 범위가 아니다.
- 리소스 모니터는 한 창만 유지한다. 열 때 선택한 카메라에 고정하고 대상 카메라명을 표시한다. 관제 선택만으로 조회 대상을 바꾸지 않는다.
- 다른 대상은 닫고 다시 연다. 해당 카메라 STOP 시 연결된 모니터를 정리하고, 무관한 카메라 STOP은 모니터 때문에 막히지 않도록 한다.
- 전체 보기에서 모니터 대상도 모호하므로 카메라 선택을 요구하는 UI가 적절하다.

## 7. 실행·요청·종료의 무결성

### 7.1 시작 요청과 최대 두 슬롯

- START 전 기존 상세 API로 최신 입력 주소·활성 상태를 확인한다.
- 상세 조회 실패·비활성 응답이면 실행하지 않는다.
- 조회 준비부터 슬롯을 예약한다. 연결 준비·재연결·중지 중에도 슬롯은 점유한다.
- 같은 카메라 중복 요청 및 두 슬롯을 초과하는 요청을 관리자에서도 차단한다. 버튼 비활성화만으로 방어하지 않는다.
- 카메라별 요청 식별 정보를 보관한다. `CameraApiClient`를 카메라별로 사용하는 방식을 우선 고려하고 HTTP 내부를 불필요하게 재작성하지 않는다.
- 조회 취소·실패 때 예약을 회수한다. 한 요청의 취소가 다른 카메라 요청을 취소하지 않는다.
- 조회 중 사용자가 화면 선택을 바꿔도 원래 요청 카메라만 실행한다.

### 7.2 결과 식별

- 프레임·상태·오류·통계 전달은 `camera_id + 실행 식별 정보`로 구분한다.
- 기존 `run_generation` 방식은 카메라별로 적용하거나 동등한 실행 토큰으로 구현한다.
- STOP 이후, 재시작 이후, 로그아웃 이후 도착한 이전 응답·신호를 무시한다.
- 신호를 연결할 때 선택 카메라 전역값을 참조하여 결과 소유자를 결정하지 않는다.
- 로컬 인물은 `camera_id + 실행 + local_person_id` 범위에서 해석한다. 다른 카메라의 같은 숫자 ID를 동일인으로 취급하지 않는다.
- 현재 파일 격리용 UUID는 미래 이벤트 설계의 `tracking_run_id`와 동일한 값이 아니다.

### 7.3 개별 STOP과 전체 종료

- 개별 STOP: 해당 시작 요청 취소 → Worker 종료 요청 → 녹화·클립·RTSP·복구 등 정리 확인 → 객체 회수·슬롯 반환.
- 다른 카메라는 수신·추적·저장·제어가 계속 가능해야 한다.
- 정리 중인 카메라를 재시작하거나 슬롯을 조기 재사용하지 않는다.
- GUI 스레드에서 긴 `wait()`/join으로 종료를 기다리지 않는다. 기존 타이머 기반 비동기 확인 방식을 확장한다.
- 전체 종료: 새 START 차단 → 모든 시작 요청 취소 → 모든 Worker 정리 요청 → 모니터·설정 등 정리 → 모든 결과 확인 → `shutdown_complete` 통지.
- `AppController`의 기존 `begin_shutdown()` → `shutdown_complete` → 세션 로그아웃 → 소유한 백엔드 종료 흐름을 유지한다.
- 비정상 Worker 종료, 정리 지연, 정리 실패를 카메라별로 구분한다. 실패한 정리를 정상 완료로 보고하지 않는다. 다른 카메라의 STOP까지 막지 않는다.

## 8. 유지할 녹화·클립·궤적 정책

### 8.1 기존 저장 위치

```text
선택한 저장 루트/
  cameras/camera_<DB ID>/<실행별 UUID>/
    crops/
    원본 녹화본/
    이벤트 CLIP/
    복구 영상/
```

- 기존 파일을 이동·삭제하지 않는다. 이번 작업에서 `이벤트 CLIP`이라는 폴더명도 굳이 바꾸지 않는다. 이벤트 UI 비활성화가 파일 저장 중단을 뜻하지 않는다.
- 저장 경로 미설정 시 기존처럼 원본 녹화·클립·복구는 실행하지 않는다.
- 원본 녹화는 기존 분할 정책을 유지한다.
- 복구는 해당 카메라의 시작 시 확정된 장치 API URL과 실행 폴더를 사용한다. 복구 파일 완료는 LIVE 판정과 다르며 실제 새 프레임으로 연결 회복을 판단한다.

### 8.2 인물별 클립

- `ClipManager`를 카메라마다 독립적으로 사용한다.
- 인물의 추적 상태가 만들어지면 고유 폴더를 만들고 `preview.mp4`를 저장한다.
- 기본 최대 길이는 10초이며 기존 설정값을 따른다.
- 인물만 crop한 영상이 아니라 **박스를 그리기 전 전체 영상 프레임**을 저장한다.
- 최대 시간이 지나면 같은 상태의 추가 클립을 계속 생성하지 않는다. 추적 상태가 끝나고 새 상태가 생기는 경우는 별도다.
- crop이 없어도 클립 저장은 가능하다. 이번에는 `full_crop.jpg` 생성을 완료 기준에 넣지 않는다.

### 8.3 궤적

- bbox 하단 중앙점을 사용한다.
- 현재 기본값: 갱신 5회 간격 샘플링, 최소 이동 거리 10px, 평활화 계수 0.35, 저장 시 단순화 epsilon 4.0. 급격한 점프 필터도 유지한다.
- 클립이 끝난 뒤에도 인물이 추적되는 동안 궤적 수집은 계속된다.
- 인물 추적 종료 또는 `finish_all()`에서 마지막 프레임 위에 궤적을 그려 `trajectory.jpg`를 저장한다.
- 클립과 궤적의 시간 범위가 다를 수 있다. 모든 시간의 움직임을 클립이 포함한다고 설명하지 않는다.
- 궤적은 카메라 영상 좌표계의 경로다. 두 카메라 궤적을 하나의 공간 경로로 합치는 기능은 이번 범위가 아니다.

### 8.4 필수 보완: 단선 중 인물 정리

현재 Worker는 프레임이 없으면 다음 수신으로 넘어가므로 `remove_disappeared_persons()`가 새 프레임까지 지연될 수 있다.

- 프레임이 없는 동안에도 마지막 관측 시각과 기존 인물 유실 기준(현재 3초)을 이용해 정리할 수 있도록 보완한다.
- 만료된 인물의 클립을 닫고 궤적을 마무리한다. 가짜 프레임이나 가짜 탐지 결과를 만들지 않는다.
- 단선·재연결 시 이미 종료한 관측의 궤적이 다른 사람에게 이어지지 않는지 확인한다.
- 장기 단선 후 추적기 내부 상태를 어떻게 초기화할지는 구현 시 `PersonTracker`의 ID 보정과 함께 확인한다. 초기화한다면 내부 추적 실행 식별도 구분한다. 짧은 일시 지연마다 무조건 모델을 재로딩하지 않는다.

### 8.5 유지 정책의 한계와 검증

- 인물별 전체 프레임 인코딩이므로 동시 등장 인물이 많으면 인코더·디스크 부하가 증가한다. 두 카메라 각각 여러 사람이 있는 조건을 검증한다.
- 처리 FPS가 낮으면 궤적 샘플 간 시간 간격도 커진다.
- 원본·클립은 시간 길이를 맞추려고 같은 프레임을 반복 기록할 수 있다. 파일 길이가 정상이어도 움직임이 부드러운 것은 아니다.
- 긴 지연에는 프레임 보정 한도가 있어 구간을 건너뛸 수 있다.
- 궤적 점은 수집 중 누적되고 단순화는 저장 시 수행된다. 장시간 관측의 메모리 증가를 확인한다.
- 저장 실패를 화면에서 숨기지 않는다. Writer 열기 실패와 이미지 저장 실패처럼 현재 출력/반환값 처리만 있는 경로를 점검하고, 확인된 실패는 카메라별 상태 메시지로 전달한다.
- 정책을 전면 변경하지 않는다. 데이터 손실·혼합·종료 오류는 수정하고, 시간 기반 샘플링이나 공유 클립 저장 같은 정책 변경은 측정 후 별도 범위로 다룬다.

## 9. 후속 crop·이벤트·OSNet·CNN을 위한 경계

사용자가 생각하는 후속 순서:

```text
crop 저장 정책 수립
  → 저장 성공 후 새 이벤트 생성
  → OSNet 특징 추출·동일인 판단
  → 글로벌 person ID 연결
  → 자체 CNN 이미지 분석
  → 이벤트에 결과·클립·궤적 연결
```

- 기존 이벤트 스키마 문서는 참고 자료다. 사용자는 새로운 이벤트 스키마로 관리할 예정이므로 구현 전에 재합의한다.
- 이번에 이벤트 테이블·API·글로벌 ID·CNN용 추상 인터페이스를 미리 만들지 않는다.
- 글로벌 ID는 카메라별 로컬 추적 ID를 대체하지 않고 여러 관측을 묶는 식별값이다.
- 파일은 로컬 관측 단위로 저장하고 나중에 이벤트가 참조하도록 한다. 글로벌 ID 변경 때 저장 폴더를 이동하는 구조로 만들지 않는다.
- 클립이 먼저 끝나고 crop·이벤트가 나중에 만들어질 수 있다. 후속 단계에는 완료 파일 경로·상태와 로컬 관측을 연결할 방법이 필요하다. 현재 `ClipManager._close_writer()`는 메모리의 `clip_path`를 비우므로 후속 연동 시 별도 결과 보존/완료 통지 설계가 필요하다. 이번에는 불필요한 DB 연동을 선행하지 않는다.
- 글로벌 매칭은 보류·실패할 수 있다. CNN이 글로벌 ID를 필수 입력으로 요구하지 않는다면 이벤트 생성 뒤 독립 실행하는 대안이 있다. **CNN을 반드시 글로벌 ID 확정 뒤에만 실행할지 아직 확정하지 않았다.** 다음 설계에서 결정한다.
- 두 카메라에서 같은 사람을 동시에 발견했을 때 중복 글로벌 ID 발급을 막는 중앙 매칭 조정은 후속 OSNet 범위다.
- 글로벌 동일인 연결과 카메라 좌표계 간 궤적 결합은 다른 기능이다.

## 10. 개발 순서와 예상 파일

### 1단계: 실행 관리자 분리

- `CameraRuntimeManager`를 추가하고 시작·상태·종료 책임을 GUI에서 옮긴다.
- 먼저 한 카메라로 기존 동작을 유지한다.
- 최신 상세 확인, 취소, 늦은 신호 차단, 정상·비정상 종료, 인증 종료 회귀 테스트를 통과시킨다.

### 2단계: 두 실행과 전체/개별 보기

- 카메라별 요청·실행 상태, 두 슬롯 제한, `CameraView`를 연결한다.
- 전체 보기 4분할과 개별 보기를 같은 GUI에서 구현한다.
- AI OFF로 동시 수신·선택 전환·개별 STOP·재시작을 검증한다.
- 이벤트 UI를 숨기고 장애 표시는 별도로 유지한다. VLM OFF가 실제 실행 경로에 적용되는지 이 단계 이전부터 확인한다.

### 3단계: YOLO·저장·유실 처리

- 두 YOLO 객체와 추적 상태를 연결하고 분리 검증한다.
- 원본 녹화·기존 클립·궤적·복구 저장 경로를 검증한다.
- 단선 중 인물 정리, 카메라별 상태·현재 인원, 모니터 대상 고정을 보완한다.
- 단일 카메라 회귀와 두 카메라 종료·오류 조건을 검증한다.

### 4단계: 실제 장치·성능 검증과 문서화

- 한 대/두 대, AI OFF/ON, 여러 인물, 단선·재연결, 반복 START/STOP을 비교한다.
- 장비와 입력 조건을 기록하고 실측 병목만 보완한다.
- README에 현재 구현·검증 결과·남은 제한·후속 작업을 남긴다.

| 파일 | 계획 |
| --- | --- |
| 신규 `cameras/runtime_manager.py` | 실행 관리자와 필요한 최소 실행 상태 정의 |
