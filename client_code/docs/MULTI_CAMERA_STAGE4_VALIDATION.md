## 2. 측정 방법

`tests/manual_multi_camera_probe.py`는 명시적으로 실행하는 진단 스크립트이며 자동 unittest 탐색에 포함되지 않는다.

- 카메라 등록은 SQLite를 읽기 전용으로 읽는다. 이는 진단 입력 선택용이며 PyQt 제품의 HTTP 접근 경계를 변경하거나 API 로그인 흐름을 검증한 것이 아니다. 원본 카메라 URL·자격증명·오류 원문은 보고서에 기록하지 않는다.
- 실제 `VideoWorker`/`VideoStream`/`PersonTracker`/저장 관리자를 실행한다. Qt는 offscreen 이벤트 루프다. 표시 위젯의 사용자 조작이나 실제 모니터에서의 시각적 지연을 측정한 것은 아니다.
- 모든 Worker가 10개 프레임을 전달한 뒤 측정 구간을 시작한다. FPS는 해당 구간의 프레임 신호 전달 간격으로 계산한다. 초기 모델 준비 시간을 제외한 정상 처리율이며 첫 프레임 시간은 별도로 기록한다.
- 추론 시간은 실제 `PersonTracker.track()` 호출 전체의 경과 시간이다. 모델 추론뿐 아니라 전후 처리·추적·결과 변환도 포함하며 처음 10회는 요약에서 제외한다.
- CPU/RSS/CUDA 할당을 약 1초, `nvidia-smi` 전체 GPU 사용량을 약 2초 간격으로 표본 수집한다. GPU 사용량은 다른 프로세스·디스플레이도 포함한다. psutil 프로세스 CPU 백분율은 논리 코어 수로 나눈 값이 아니다.
- 종료 확인 타이머는 1초 주기이므로 약 1초의 종료 수치는 정밀한 해제 시간으로 해석하지 않는다.
- 생성된 모든 MP4를 끝까지 디코딩하고 프레임 수·파일 FPS를 기록했다. JPEG는 한글 경로에서 디코딩했다. 디코딩 가능하다는 사실은 장면의 정확성·무손실 녹화·움직임 품질을 보장하지 않는다.
- 매 실행의 `report.json`, 반복 시험의 `after_cleanup.json`, 영상은 `client_code/outputs/stage4/<label>/`에 보존했다. 녹화물은 로컬에만 있으며 외부로 전송하지 않았다.

## 3. 처리율 비교

| 실행 label | 입력 / AI | 측정 구간 | FPS | 프레임 간격 p95 | 추적 호출 평균 / p95 |
| --- | --- | --- | --- | --- | --- |
| `webcam_off_01` | 실제 웹캠 / OFF | 20초 | 16.53 | 89.23ms | 해당 없음 |
| `webcam_on_01` | 실제 웹캠 / ON | 20초 | 8.80 | 147.99ms | 36.23 / 58.71ms |
| `replay_one_on_01` | 녹화본 1개 / ON | 20초 | 22.62 | 55.20ms | 27.98 / 36.28ms |
| `replay_two_off_01` | 녹화본 2개 / OFF | 20초 | 23.80 / 23.80 | 45.93 / 46.43ms | 해당 없음 |
| `replay_two_on_01` | 녹화본 2개 / ON | 30초 | 16.37 / 16.32 | 79.32 / 77.92ms | 43.30 / 51.94ms, 43.27 / 51.09ms |
| `webcam_restart_cycle1` | 실제 웹캠 / ON | 12초 | 15.94 | 162.18ms | 25.94 / 50.84ms |
| `webcam_restart_cycle2` | 같은 프로세스 웹캠 재시작 / ON | 12초 | 7.56 | 176.40ms | 40.82 / 66.15ms |

카메라를 켠 시간 전체가 아니라 워밍업 후 요청한 측정 구간이다. 종료·표본 타이머 때문에 실제 구간은 조금 길 수 있다. 환경·장면·카메라 노출·다른 프로세스 부하를 고정한 실험이 아니므로 서로 다른 실행의 차이를 전부 AI 비용으로 귀속하지 않는다.

- 초기 웹캠 OFF/ON 실행은 인물 검출 0이었다. 뒤의 실제 웹캠 재시작에서는 각각 최대 2개/1개 인물을 검출했고 클립·궤적이 저장됐다. 정답 라벨이나 다수 인물이 일정 시간 머무는 통제 실험은 없으므로 사람 수·검출 정확도의 보증은 아니다.
- 녹화본 재생에서는 실제 모델이 최대 1개 인물을 검출했다. 두 Worker의 인물 클립·궤적은 각각 다른 카메라/실행 폴더에 저장됐다.
- 웹캠 첫 실행의 프레임 읽기는 AI OFF 평균 51.24ms, AI ON 평균 66.22ms였다. 재시작 두 실행에서는 평균 25.69ms/63.01ms였다. 영상 읽기와 추론이 같은 Worker 루프에 있으므로 두 시간이 모두 갱신 간격에 반영된다. 수신 대기의 원인이 노출·드라이버·버퍼 중 무엇인지까지 분리하지 않았다.
- `webcam_on_01` 첫 프레임은 시작 후 약 13.54초, 실제 웹캠 재시작은 7.91초/1.44초였다. 모델 초기화·첫 추론·장치 열기 비용이 포함된다. 정상 스트리밍의 통신 지연과 구분한다.
- 첫 AI 실행 원본의 10초 구간 파일은 디코딩 길이가 약 7.17초였다. 최초 추론 지연과 기존 프레임 보정 상한 때문에 녹화 길이·움직임이 벽시계와 일치하지 않을 수 있음을 실측했다. 정책을 임의로 바꾸거나 이를 정상적인 무손실 녹화라고 처리하지 않았다.

## 4. 자원·저장·종료

| 조건 | 프로세스 RSS 최고 | 전체 GPU 사용 메모리 최고 |
| --- | --- | --- |
| 웹캠 최초 OFF / ON | 488 / 1,316 MiB | 이 두 실행은 GPU 전체 표본 수집 전이며 미측정 |
| 재생 한 모델 ON | 1,346 MiB | 783 MiB |
| 재생 두 모델 OFF / ON | 546 / 1,497 MiB | 561 / 925 MiB |
| 실제 웹캠 재시작 1 / 2 | 1,364 / 1,406 MiB | 1,000 / 1,122 MiB |

두 재생 모델 ON 시험의 전체 GPU 사용률 표본 최고는 42%였다. 낮은 표본 사용률만으로 GPU 여유나 CPU 병목을 확정하지 않는다.

같은 프로세스에서 두 재생 모델을 12초씩 세 번 실행했다(`replay_restart_cycle1~3`). 각 입력 FPS는 15.52/15.44, 15.10/15.06, 16.01/15.96이었다. 매번 정상 정리했고, 종료 후 Qt 지연 삭제·Python GC를 수행한 CUDA 할당은 64 MiB, 예약은 266 MiB로 유지됐다. 종료 후 RSS는 약 1,282 → 1,289 → 1,297 MiB로 소폭 늘었다. 짧은 반복만으로 장시간 누수 부재를 결론 내리지 않는다.

실제 웹캠도 같은 프로세스에서 두 번 열고 닫았다. 종료 후 CUDA 할당 32 MiB, 예약 134 MiB가 두 번 동일했고, RSS는 약 1,303 → 1,331 MiB였다. `torch.cuda.empty_cache()`나 전역 GPU 초기화로 결과를 만들지 않았다.

완료한 10회 실행의 모든 Worker는 `cleanup_ok=true`, 저장 오류 수 0이었다. MP4 총 51개는 모두 디코딩 프레임이 있었으며 궤적 JPEG 12개는 모두 디코딩 가능했다. 실제 웹캠에서 생성된 인물 클립·궤적도 포함한다. STOP은 각 시험의 모든 Worker에 요청했으며 실제 GUI의 선택 카메라 개별 STOP/보기 전환은 이번 실측에 포함하지 않았다. 해당 동작의 3단계 자동 회귀 결과와 구분한다.

## 5. 목표 판정과 남은 검증

**통신 지연 2초 미만: 판정 불가.** 엣지노드·실제 네트워크 입력이 없으며 센서 촬영 시각과 최종 화면 표시 시각도 계측하지 않았다. 프레임 갱신 간격 또는 YOLO 추론 시간이 2초보다 작다는 이유로 통신 지연 목표를 통과 처리하지 않는다.

**버벅임 최소화: 추가 확인 필요.** 웹캠 AI ON 처리율이 실행별로 7.56~15.94 FPS로 변했고 p95 갱신 간격도 148~176ms 수준이었다. 평균 FPS만으로 안정성을 통과 처리하지 않는다. 장치/노출/다른 부하를 고정한 비교와 화면 체감 검증이 필요하다. 최소 FPS와 허용 정지 구간의 수치를 정한 뒤 합격 기준으로 사용한다.

남은 항목:

- 실제 카메라 두 대 또는 웹캠+엣지노드 동시 수신, 입력 해상도·FPS·네트워크 조건 고정.
- 동기화된 타임코드 또는 화면 타이머로 촬영→최종 표시 지연을 측정하고 통신 지연 2초 미만 확인.
- 실제 관제 창에서 전체/개별 보기 전환·개별 STOP·로그아웃과 다른 카메라 저장 유지 확인.
- 실제 RTSP 단선·재연결, 해당 장치 복구 API 및 FFmpeg 병합 재생 확인.
- 여러 인물의 지속 등장 조건, 장시간 모델/메모리/궤적 누적과 인코딩 부하.
- 카메라 수신 변동과 첫 추론 지연을 분리한 후 필요한 범위의 최적화. 공용 모델·TensorRT·crop 정책 변경은 선행하지 않는다.

## 6. 다시 실행하는 방법

실행 디렉터리: `C:\GitHub_Clone\AI_CCTV`. 기존 관제 프로그램이 같은 웹캠을 사용 중이면 먼저 그 프로그램에서 정상 STOP한다. 스크립트는 다른 프로세스를 종료하지 않는다.

```powershell
# 등록 메타데이터와 CUDA 환경 확인. 등록된 RTSP/장치 API의 TCP 포트도 확인한다.
.\venv311\Scripts\python.exe -B client_code/tests/manual_multi_camera_probe.py --environment

# 실제 등록 카메라 2번, 워밍업 후 30초, 실제 YOLO 사용
.\venv311\Scripts\python.exe -B client_code/tests/manual_multi_camera_probe.py --ids 2 --ai --seconds 30 --label webcam_new_run

# 같은 프로세스에서 세 번 시작/종료
.\venv311\Scripts\python.exe -B client_code/tests/manual_multi_camera_probe.py --ids 2 --ai --seconds 15 --cycles 3 --label webcam_repeat_new

# 두 입력 보조 부하 시험. 실제 두 카메라 검증이 아님.
$probeInput = Get-ChildItem client_code/outputs/stage4/webcam_off_01 -Filter '*.mp4' -Recurse | Select-Object -First 1 -ExpandProperty FullName
.\venv311\Scripts\python.exe -B client_code/tests/manual_multi_camera_probe.py --replay $probeInput --copies 2 --ai --seconds 30 --label replay_new_run
```

`--ai`를 생략하면 AI OFF다. `--label`은 매번 새로운 이름을 사용한다. 기존 측정 폴더가 있으면 덮어쓰지 않고 거부한다. 장치가 없거나 프레임/종료가 정상적이지 않으면 JSON의 오류·프레임 수·cleanup 값을 확인하며, 프로세스 종료 코드만으로 합격 판정하지 않는다. 카메라 드라이버의 read/release가 반환하지 않는 경우 강제 종료 대신 정리 대기가 길어질 수 있다.
